# STRAP II as a 7030 program: the reconstruction's design

`docs/reconstruction_plan.md` §7 step 4: STRAP II is written host-side first
(`strap/strap2/`, the executable specification). Then it is written as a 7030
program, assembled by the host-side one. "Completeness is checked by
self-hosting: the 7030 STRAP II assembles its own source to the same bits."
This file holds the conventions of that 7030 program, as `smac_7030.md` does for
SMAC. Each one cites the page it comes from, read in the ink, or is marked
**CHOSEN** with its reason. Page numbers are C22-6729's printed pages unless
another document is named. The 7030 version is a RECONSTRUCTION: no listing of
STRAP II survives except one page (CHM 102633945,
`decks/strap2_chm102633945.strap`).

## Environment: what stands in for MCP (all CHOSEN)

MCP does not yet run jobs on the model (`programming_environment.md` E1-E4), so
the 7030 STRAP II starts the way the 7030 SMAC does: an image loaded straight
into core.

- **COMREC** is a 25-word table at a fixed address. Its words 7.32-13.17 are
  set by the test harness as a pre-processor would set them (p.8: "This word
  must always be set up by the pre-processor").
- **Input** is a block of card images in core in **IQS**, code 5, ten words per
  card, ending at a count. IQS is the code SMAC hands STRAP II (C22-6729 p.7's
  chain; `smac_7030.md`), so the SMAC-to-STRAP path is the real one.
- **The disk files** (the intermediate files, the name file, the listing and
  the binary) are blocks in core. Each is written in p.10's arc format: header
  index word, dummy word, data. Replacing the in-core blocks with the disk
  (`disk_subsystem.md`) then changes only the I-O routine.
- **The overlay** (SCSTRAP2 replacing A1 and 1, p.174) is kept as a layout. At
  first the harness loads both images. Loading SCSTRAP2 from the disk at the
  end of Pass 1 waits for MCP's loader.

## The unit layout: two options, kept (preserve every option)

Figure 20 (p.189) puts ZIOTPT in fixed word 5, counting ZIADAB as word 0. The
host follows it (`strap2/unit.py`, `_W6` from the control word). The one
surviving page of STRAP II addresses ZIOTPT as word 4 (`4.00`), and its other
fields agree with Figure 20 bit for bit (the deck's header). So the 7030
source defines every Z field by SYN in one place, and keeps both layouts as a
build option: FIG20 (the default; the host matches it, so dumps compare) and
CHM (the page's). The CHM page's own lines are assembled in the CHM layout and
must print its machine code.

## Acceptance

Self-hosting alone exercises only the constructs STRAP II's source uses. So
the 7030 STRAP II is also checked against:

1. the printed anchors: C22-6678-1 p.48 (`verify_mcpref_example2_listing.py`)
   and the CHM page, both run through the 7030 assembler;
2. MCP decks against their `!CHECK` rows: a sample in the suite and all of them
   in a long run whose result is recorded;
3. the host STRAP II, phase by phase: units, symbol table and coded expressions
   compared bit for bit after Pass 1, after UITER and after 2b.

**The source subset.** The 7030 STRAP II's source may use only what both the
host STRAP II and the 7030 one accept. The list is kept here as it grows.

## The order of work

Each step is one commit, the suite green, injected into the 7030 deck itself
(each injection is a Bluesim run, so budgeted).

1. **The thin slice: input and GETCHA.** COMREC, the IQS card block, and
   GETCHA (pp.77-79, 203-205) delivering A8 characters in $3, with $14 its own. Test:
   the characters GETCHA returns for a set of cards (continuations, comments,
   columns 73-80) equal the host `Getcha`'s. **Measure the model steps per
   card.** That number decides what the suite can run and what becomes a
   recorded long run.
2. GETFLD with CPLTNM and CPLTSY, and the coded-expression encoder (pp.70-76,
   80-86; Appendix C pp.197-201).
3. TABMAN and the symbol table (pp.13, 43-53; Figs. 8, 21, 22).
4. MAIN with BOPSER and the pseudo-operations (pp.14-27, 79-134), Pass 1 complete: dump units and
   the symbol table, compare with the host.
5. VALUE (pp.54-60), UITER, Pass 2a (pp.28-36).
6. DECODE and OUTPUT, Pass 2b (pp.135-172); the punch; the listing.
7. Self-hosting: the 7030 STRAP II assembles its own source to the same bits.

## Status

**Step 1 done, 2026-11-12**: `decks/strap2_7030.strap` holds XINPUT (IQS to
A8 through a 256-byte table, IQSA8) and GETCHA, with DRIVE standing in for
MAIN. `tests/check_strap2_7030.py` assembles it with the host STRAP II, loads
it from STRAP II's own binary deck (`gen_tb.py ASM=strap2`), runs it on the
model, and compares every character and every block name with strap2's
Getcha: 15 cards, 132 characters, 10 names.

**The measured cost**: 274,565 model steps for those 15 cards, about 18,300 a
card, DRIVE and the load included, and 8 s of Bluesim (about 34,000 steps a
second). So GETCHA alone over a source of 4,000 cards would be about 73
million steps, half an hour. The whole assembler will cost many times that,
so self-hosting will be a recorded long run, not a suite case; the suite runs
small decks per phase.

What step 1 taught:
- **LVI loads a half-word address.** The bits below .32 are dropped, so
  `LVI,$3,.29` gave 0 and `LVI,$7,GCCARD+.8` gave GCCARD. An address with a
  bit part is loaded with LV from an XW, and a character reaches $3 through a
  store (GCPUT).
- **The host gave MAIN a comment block's characters**, against p.79 ("without
  giving them out to main flow through $3"). Fixed in `strap2/cards.py`.
- CHOSEN, as the host: the initial card's name loses its trailing blanks
  before a continuation card adds to it; p.79 does not say.

Not written yet in GETCHA: Gcaz (blanks significant, p.102), the
statement-buffer Bsyst, GNLOAD's name file, the coprocessor exits (boxes 5-8,
11-13, 17-19, 25-26), XINPUT's duplicating mode (DUPLI, p.27), and the
statement comment in columns 10-72 (MAIN's, p.79).
