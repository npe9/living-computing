# STRAP II as a 7030 program: the reconstruction's design

`docs/reconstruction_plan.md` §7 step 4: STRAP II is written host-side first
(`strap/strap2/`, the executable specification). Then it is written as a 7030
program, assembled by the host-side one. "Completeness is checked by
self-hosting: the 7030 STRAP II assembles its own source to the same bits."
This file holds the conventions of that 7030 program, as `smac_7030.md` does for
SMAC. Each one cites the page it comes from, read in the ink, or is marked
**CHOSEN** with its reason. Page numbers are C22-6729's printed pages unless
another document is named. The 7030 version is a RECONSTRUCTION: no listing of
STRAP II survives except one page (CHM 102633945,
`decks/strap2_chm102633945.strap`).

## Environment: what stands in for MCP (all CHOSEN)

MCP does not yet run jobs on the model (`programming_environment.md` E1-E4), so
the 7030 STRAP II starts the way the 7030 SMAC does: an image loaded straight
into core.

- **COMREC** is a 25-word table at a fixed address. Its words 7.32-13.17 are
  set by the test harness as a pre-processor would set them (p.8: "This word
  must always be set up by the pre-processor").
- **Input** is a block of card images in core in **IQS**, code 5, ten words per
  card, ending at a count. IQS is the code SMAC hands STRAP II (C22-6729 p.7's
  chain; `smac_7030.md`), so the SMAC-to-STRAP path is the real one.
- **The disk files** (the intermediate files, the name file, the listing and
  the binary) are blocks in core. Each is written in p.10's arc format: header
  index word, dummy word, data. Replacing the in-core blocks with the disk
  (`disk_subsystem.md`) then changes only the I-O routine.
- **The overlay** (SCSTRAP2 replacing A1 and 1, p.174) is kept as a layout. At
  first the harness loads both images. Loading SCSTRAP2 from the disk at the
  end of Pass 1 waits for MCP's loader.

## The unit layout: two options, kept (preserve every option)

Figure 20 (p.189) puts ZIOTPT in fixed word 5, counting ZIADAB as word 0. The
host follows it (`strap2/unit.py`, `_W6` from the control word). The one
surviving page of STRAP II addresses ZIOTPT as word 4 (`4.00`), and its other
fields agree with Figure 20 bit for bit (the deck's header). So the 7030
source defines every Z field by SYN in one place, and keeps both layouts as a
build option: FIG20 (the default; the host matches it, so dumps compare) and
CHM (the page's). The CHM page's own lines are assembled in the CHM layout and
must print its machine code.

## Acceptance

Self-hosting alone exercises only the constructs STRAP II's source uses. So
the 7030 STRAP II is also checked against:

1. the printed anchors: C22-6678-1 p.48 (`verify_mcpref_example2_listing.py`)
   and the CHM page, both run through the 7030 assembler;
2. MCP decks against their `!CHECK` rows: a sample in the suite and all of them
   in a long run whose result is recorded;
3. the host STRAP II, phase by phase: units, symbol table and coded expressions
   compared bit for bit after Pass 1, after UITER and after 2b.

**The source subset.** The 7030 STRAP II's source may use only what both the
host STRAP II and the 7030 one accept. The list is kept here as it grows.

## The order of work

Each step is one commit, the suite green, injected into the 7030 deck itself
(each injection is a Bluesim run, so budgeted).

1. **The thin slice: input and GETCHA.** COMREC, the IQS card block, and
   GETCHA (pp.77-79, 203-205) delivering A8 characters in $3, with $14 its own. Test:
   the characters GETCHA returns for a set of cards (continuations, comments,
   columns 73-80) equal the host `Getcha`'s. **Measure the model steps per
   card.** That number decides what the suite can run and what becomes a
   recorded long run.
2. GETFLD with CPLTNM and CPLTSY, and the coded-expression encoder (pp.70-76,
   80-86; Appendix C pp.197-201).
   **First, the host's lookahead.** The 7030 GETCHA gives one character in $3
   and keeps no pushback, but the host peeks ahead on the card in six places:
   `getfld.py` `_peek_gp` (is `(` a gp, `(.n)` or `(r,.n)`?), `_closes_field`,
   and `_radix_prefix` (through `_radix_ahead`, which saves and restores
   GETCHA's state: `(8)` before a number); `pass1.py` `_dim_parens` (a DR's
   dimension list) and `_field_entry` (a numeric DD field's `(Fn)` or radix).
   Each reads `g.card` directly and stops at column 72, so none sees across a
   continuation card. Before GETFLD is written, read for each how the chart
   decides (GETFLD box 74, Gfsrad, for the radix), or write a $14 peek and mark
   it CHOSEN. Then test a prefix split across a continuation card on both.
   **The printed oracle first**: `check_strap2_coded.py`'s vectors (Appendix
   C, Figs. 28-29) run through the 7030 GETFLD directly, before any comparison
   with the host.

   **The lookahead, resolved 2026-11-13** (Charts BI-BK pp.80-82, text
   pp.83-85, read in the ink). GETFLD classifies a parenthesis at its `)`, from
   what it holds and what came before it, and reads no character past it:
   Box 64 "ONE ABSOLUTE DATUM ONLY", 65-66 a g.p., 79 "SUBSCRIPT ALLOWED"
   (Gfsfsb, on only after a programmer symbol, Boxes 25-27), 80 no operators,
   81 and 74 the radix into Gfsrad; 76-78 arithmetic, 82 S/X. So the host's
   three GETFLD peeks are gone: `_radix_prefix`/`_radix_ahead`, `_closes_field`
   and GETFLD's use of `_peek_gp` became `getfld.py` `_paren`, which parses the
   parenthesis and then classifies it. Every deck's coded expressions are
   unchanged (all 70,126 fields in the 734 decks, encode() before and after);
   `tests/check_strap2_getfld_paren.py` pins the inputs where the two rules
   differ, a prefix split across a continuation card among them.
   - CHOSEN: Box 76 "ARITHMETIC PARENTHESES LEGAL" has no drawn test; it is
     taken as an operator inside (Boxes 43-49) at the start of a datum. MCP
     p.126's `KV,2,($1)` (000000.04 91) and Fig. 29's `7.(3-6*18)($X2+3.0)`
     both agree with it.
   - CHOSEN: `L,(3)`, a radix with no datum after it, is refused (66).
   - OPEN: Box 66 tests ".L OPERATOR" for `(.n)`, where p.198 codes `.2` as
     `.R`. Box 69 removes the operator and 70 restores the buffer, so it never
     reaches the output; `_paren` takes the form `.n`.
   - OPEN: the chart reads the radix's digits and a g.p.'s n with CPLTNM, so
     in the radix then in force (Gfsrad is zeroed only at instruction
     initialization, p.70). The host reads the radix and n as written in
     decimal (`Datum.text`), as before; no deck tells them apart.
   - **The 7030 GETFLD's shape**, from the chart. Data go into the coded
     expression in order as they are read (Boxes 17, 24, 26-29); operators,
     each with its datum number, wait in the GETFLD buffer and are put in
     after the data by GFZA (Boxes 43, 60). A point is an operator of the
     top priority (p.198): `.b` waits as `.R`; `a.` waits as `.L` and
     becomes `.+` when a datum follows (Boxes 58-59). So the parser has two
     states, a datum expected and after a datum, and the operator stack;
     everything else an expression needs lives in a frame (stack floor,
     data count, its operators' start, its region, where its `(` stood).
     A `(` opens a sub-expression (Box 2 pushes the buffer one word). At the
     `)` it becomes S/X (GFZA, prefix 1000, Boxes 56, 60: p.199 note 2's
     "the 1 of 2E is the 1A of the inner expression"), joins the outer data
     and operators (Box 78, arithmetic), or is taken back out (Box 70: a
     g.p. or a radix). CHOSEN: each parenthesis is built in a scratch region
     and copied to its place at the `)`, not built in place, because the
     zero datum of `($1)` (MCP p.126) must stand before the content, and
     which it is is known only at the `)`. A datum's end bit is written
     only when no `(` follows it. Sub-slices, each tested against the host
     field by field: (a) numbers (CPLTNM, in floating point as Box 1
     says), programmer symbols (CPLTSY Boxes 1-11, no tails), the
     operators; (b) parentheses, Fig. 28 first, a radix or g.p. halting 9
     until (d) (done); (c) `$` and system symbols, BOPSER over a table
     generated from the host, and MBSPEC (done); (d) g.p. and radix (done).
   - Not GETFLD's: MQDD's numeric DD (`pass1.py` `_field_entry`, and its
     `_peek_gp`/`gp_chain`) and the DR dimension list (`_dim_parens`) still
     look ahead. They are MAIN's, step 4: read MQDD boxes 6-19 (p.71 says
     GETFLD does not collect a numeric DD's numbers) and MDIMRF then.
3. TABMAN and the symbol table (pp.13, 43-53; Figs. 8, 21, 22). Read in the
   ink 2026-11-13: pp.13, 38, 43-49 and 190.
   - **3a: a host TABMAN** (`strap2/tabman.py`), standalone and generic.
     - It covers the Fig. 8 control block, MOVE, SEARCH, ADDUNO, ADDORD,
       ANEXT and RSERCH, written to pp.40-53.
     - It has its own test, with measured injections, covering:
       - the delete mark (a deleted match is a miss, p.43 Box 11; ADDUNO
         replaces a deleted last entry, p.49);
       - ADDORD on an unordered table;
       - the not-found index words (ordered: the next higher entry;
         unordered: the location after the table, p.47);
       - ANEXT's restart, and RSERCH.
     - The 7030 TABMAN (3b) is compared with it. 3b also checks the exit
       taken, FX and DX after each call, $0-$7 restored (Boxes 1-3, 31),
       and the control block at Fig. 8's printed bit positions.
   - **3c: the symbol table on TABMAN**: SymbolTable's Python map replaced.
     Two questions are open first:
     - **Order.** p.13 says ordered material is inserted "alphabetically".
       But A8 as bits is not alphabetical: digits 1-9 (1-9), 0 (10), blank
       (16), S-Z, J-R, A-I. Fig. 8's TEC "type of compare" (1 bit, meaning
       UNSPECIFIED) may be what chooses a collating compare. Read the call
       sites and the indicator and tail tables before deciding.
       - **Observability (2026-11-13).** Under any consistent total order,
         SEARCH and ADDORD give the same found / not-found and the same
         entry. Every list STRAP II prints walks the vles, not the
         dictionary: UITER, NUNDSY and PRNTALL (see Iteration). So the
         collating order shows only in a dump of the table's memory, and
         in the step count. Unless an IBM dump of a dictionary turns up,
         the plain bit compare (TEC 0) is CHOSEN and unobservable. The
         order still matters for p.44's split argument (names over eight
         characters): that compare must agree with whatever order the
         first 64 bits give.
     - **Iteration (checked 2026-11-13; this corrects the earlier claim).**
       STRAP II's walks are not in dictionary order. UITER's is ANEXT over
       the vle table (Chart GB Box 7, p.135; `docs/strap2/pass2.md` §3.1).
       NUNDSY's is too, and the host's `nundsy` already walks `st.vles`.
       - The host's three walks over `st.dictionary`:
         - `pass2.py:136`, the undefined symbols' addresses;
         - `:144`, UITER's "NO VALUE" messages;
         - `:984`, a set of error bits, which has no order.
       - Python keeps insertion order, the name's first appearance. That is
         also vle order, except for a name with more than one vle: the
         dictionary visits it once, ANEXT once per vle.
       - So 3c should change 136 and 144 to vle walks, and only programs
         with multiply defined names can be affected. Each such change is
         a finding, to report, not to hide.
       - p.127 (MULTI, read in the ink 2026-11-13):
         - MAIN enters a symbol with ADDORD, and "ADDORD effectively went
           to MULTI" from its already-there exit.
         - A legal multiple repoints the dictionary at the new vle. One
           with contradictions leaves it on the first ("The symbol table
           entry for the first 'B' is used in all references").
         - Every name encountered has at least a basic vle, and MULTI adds
           one more for each multiple definition.
         So ANEXT does visit a multiply defined name more than once. 3c's
         vle walk at `:144` can give "NO VALUE" for a vle the dictionary
         no longer holds; the host gives it at most once per name.
       - Which routine gives undefined symbols their addresses is still
         `pass2.md` Gap 3, UNSPECIFIED. "In the order encountered" (p.205,
         C28 p.20) agrees with the vle walk.
   - **Readings for 3a** (CHOSEN where marked):
     - An entry is Fig. 21's: delete bit, vle bit, argument (AL bits),
       function (ADDL bits). CHOSEN: EL is 2+AL+ADDL rounded up to a half
       word, because FW and LW are half-word addresses (p.45). That gives a
       symbol 96 bits, a tail 64 and an indicator 64.
     - The vle is TABMAN's (p.44: "Whenever an entry either exceeds
       established fixed length limits or whenever it is desired to split
       the argument, a variable length entry (vle) is established").
       - When al > AL or fl > ADDL, the vle takes Fig. 22's head (the
         table's Azid as its ID), the argument's remainder and the
         function.
       - The dictionary's function field is the vle's signed address, and
         its vle bit is 1.
       - Agetv gives the function address past the head and remainder.
         The host's `SymbolTable._vle` already lays it out this way.
     - **The exits (Gap 11, `pass2.md`).** With $15 at `tbl` and the exit
       `B,-1($15)` one halfword back, SEARCH and ADDUNO close against their
       linkages: found +2.32, not found +2.0, ADDUNO +3.0. ADDORD's
       already-there is +2.32 then +0.32 (Boxes 32-33). Box 9's +3.32 would
       exit at 3.0, the error exit, where p.46 Boxes 8-9 and p.48 say
       normal. CHOSEN, as before: follow the text, so normal (3.32), and
       an unordered table's ADDORD takes the error exit after ADDUNO adds
       the entry at the end (p.48).
     - Linear against binary search (p.45 Box 7: under seven entries, or
       an unordered table) gives the same results. It is unobservable
       except by a step count, so the 7030 test pins it by steps or not at
       all, and says which.
4. MAIN with BOPSER and the pseudo-operations (pp.14-27, 79-134), Pass 1 complete: dump units and
   the symbol table, compare with the host.
5. VALUE (pp.54-60), UITER, Pass 2a (pp.28-36).
6. DECODE and OUTPUT, Pass 2b (pp.135-172); the punch; the listing.
7. Self-hosting: the 7030 STRAP II assembles its own source to the same bits.

**Step 2, sub-slice d done, 2026-11-13**: the g.p. and the radix, classified
at the `)` like every parenthesis.
- **The g.p.** One item `.n`, or two items `.n,r` / `r,.n` (C28-6129 p.25,
  p.30), is a g.p. at any of the three places a `(` may stand.
  - After a point the `.L` stays, as in strap2.
  - The outer depth must be 0 (p.207; otherwise 166).
  - Its items' operators are spent, as for S/X.
  - The field's operators are put, then Boxes 37-38: `1`, n in 6 bits, and
    the value, an expression of its own in radix r (none: 10).
  - A field with no data before its g.p. is null (`(.3)5`), as strap2.
  - No value is 166.
- **The radix.** One lone absolute item at a datum's start, or after a
  point, is a radix.
  - At a datum's start, the datum follows.
  - After a point, the datum the point joins follows. A `(` there opens at
    a datum's start and turns the `.L` into `.+` when it closes (Boxes
    58-59, as strap2's `A.(8)(B+1)`).
- **Read as written.** n, r and a radix are read as written, in decimal:
  CPLTNM keeps the digits' decimal value beside its floating-point one
  (CPDEC), and each item's record holds it. So `(8)7+A(.12)9` has n = 12,

**The error routine waits for step 4** (p.38, read in the ink 2026-11-13).
- ERR's entry is 32 bits: the Unit counter (20 bits), the Field counter
  (4) and the message number (8). Unit and Field are MAIN's serviceability
  counters.
- An error is raised by `EX` of the message's CW instruction. That causes an
  execute exception, MCP passes it to ERR through STRAP II's exit table,
  and ERR "returns to MCP in order to resume assembly processing".
- So no message stops the assembly. The 7030 program's 100+n halts, and
  the NOTEC/NOTEL notes, stand in for ERR until MAIN and the MCP exit
  exist. Message 63 (a digit too large; p.71 says the digit is still used)
  is then a recorded error that carries on, as 129 already does.
