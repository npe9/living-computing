# OCR text of the scanned documents

Machine-generated by `tesseract` from the PDFs in `docs/`. Built
2026-10-25.

## >>> THIS IS A FINDING AID. IT IS NOT A SOURCE. <<<

**Nothing in this directory may be transcribed into a deck, quoted as
a citation, or used to settle a reading.** Every character here came
out of an OCR engine, and for the MCP listing it came out of an OCR
engine pointed at a 1963 drum-printer scan whose typography has forty
sections of `docs/listing_typography.md` devoted to why it cannot be
trusted one glyph at a time.

Measured, on printed p.80 where this project has verified ground
truth from `decks/mcp_bootstrap_p80.strap`:

```
location column   11/11 exact   (after the C->0 rule of 13e)
code column        2/11 exact   -- mostly FO for F0, OF for 0F
```

A hex byte cannot contain `O`, so some of that is mechanically
repairable; the rest is not. **Two engines were compared** — tesseract
and macOS Vision — and they fail differently, which is useful for
flagging disagreement and useless as a substitute for looking.

### What it IS for

The question that used to cost a render, and cost most of a day on
2026-10-25: **which page, and roughly which line.**

* which printed page defines `T PICA`, `T MESSY`, `YSCRBT`
* which page covers address 004604
* what `C28-6129` says about a construct, without rendering eight
  pages of it to find out it says nothing

`listing_index.py` answers those against the listing volumes.

### The protocol that keeps the evidence honest

A transcription is read from the IMAGE, assembled, and checked
against the listing's own printed machine code. OCR may propose a
candidate; it may never confirm one. Where OCR and the assembler
disagree, **render the ink at 1800 dpi and decide from the ink** —
which is what happened seven times on 2026-10-25, and the ink agreed
with the assembler all seven. printed p.66 line 5 is the case that
went the other way and is why `listing_typography.md` 13f exists.

> The decks are valuable precisely because they are independent
> evidence of what the listing says. An OCR-seeded deck that was then
> "corrected" until the assembler agreed would be evidence of
> nothing at all.

### Quality by document

The MANUALS are clean typeset print and OCR extremely well; `--psm 3`
handles their two-column layout. Treat them as a reliable index and
still cite the PDF page you read.

The MCP LISTING is the hard case described above. Treat it as a
page-finder only.

## Regenerating this directory

The generator ships with the artifact, because a generated file whose
generator is lost is worse than no file.

```sh
# a clean typeset manual: 300 dpi, --psm 3 (handles two columns)
docs/ocr/ocr_pdf.sh docs/22-6530-2_7030RefMan.pdf \
                    docs/ocr/22-6530-2_7030RefMan.txt 3 300 3

# the MCP listing: 600 dpi, --psm 6, cropped past the margins
docs/ocr/ocr_listing.sh docs/MCP_Mar63_001-249.pdf \
                        docs/ocr/MCP_Mar63_001-249.txt 4
```

`ocr_pdf.sh PDF OUT [jobs] [dpi] [psm]` and `ocr_listing.sh PDF OUT
[jobs]`. Both emit `===== <name> PDF page N =====` separators so a
hit can be turned back into a page to render.

**Settings were chosen by measurement, not taste.** 1200 dpi on the
listing is *worse* than 600 — it amplifies the scan's noise. `--psm
3` on the listing loses the column structure; `--psm 6` on a manual
interleaves its two columns. The listing run also carries a
character whitelist, which removes the `€ @ z` class of garbage
outright.

`listing_index.py` searches the listing volumes by symbol, address
or free text and reports **printed** page numbers (volume 1's PDF
page N is printed page N-7). It needs the listing volumes, which are
not built yet.
