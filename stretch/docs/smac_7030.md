# SMAC as a 7030 program: the reconstruction's design

The owner, 2026-11-08, asked how SMAC and STRAP II were built originally.
Both were 7030 programs written in STRAP and run under MCP, and the
owner agreed to build the 7030 SMAC now. It runs on the simulator
directly, without waiting for MCP to run jobs (`programming_environment.md`
E1-E4). `strap/smac.py`, the host-side executable specification, is the
reference its output must match card for card.

This file records every convention the 7030 version uses. A convention
either cites the page it comes from or is marked **CHOSEN**, with the
reason. All page citations are to J28-6128 (CHM 102634360) read in the
ink, unless another document is named.

## What the bulletin fixes

| item | source |
|---|---|
| one pass; a processor shell; a branch table; processor subroutines; generators | p.2 |
| "Entry to all subroutines or access to buffers is made through the branch table" | p.2 |
| all references to branch-table entries are modified by index register 2, which holds the table's address | p.2, p.13 item 3 |
| generators are relocatable routines; references inside a generator are modified by index register 1 | p.3, p.13 item 2 |
| index register 15 is used for subroutine linkage | p.13 item 4 |
| index registers 3-8 are reserved for the skeletons of the Generator Language statements' own generators | p.13 item 5 |
| index registers 9-14 are free in generator logic | p.13 item 6 |
| Generator Language statements are SMAC statements; their generators are on a special library tape, "called in only when generators are being compiled" | p.3 |
| a skeleton is put into "STRAP Data Definition statements with IQS entry mode" | p.4, errata line 33 |
| QCOUNT is the VALUE field of an index word in the branch table | p.4 as corrected by the errata |
| QLIT and QCN are value fields in the branch table | p.5, p.6 |
| QPT1-QPT5 are pointers with those symbolic tags | p.3, p.5 |
| the branch-table bits QDBUGB, QGUB, QMIBIT, QCIBIT, QMACBIT, QINBIT, QERRBIT | p.13 |

The bulletin is consistent with the linkage idiom of the one surviving
page of STRAP II's code: `SIC,$15` followed by `B,MORVAL`
(`decks/strap2_chm102633945.strap`, 000264.40-000265.00).

## How a generator becomes 7030 code

p.3 says the Generator Language statements have generators of their own,
on a library tape used when generators are compiled. So a generator's
source (MBGEN ... MEGEN) is compiled by SMAC itself, using that special
library, into STRAP. STRAP then assembles it.

- Each Generator Language statement in the logic portion expands to a
  call into the branch table: `SIC,$15` and `B,Qxxx($2)`, followed by its
  arguments as half-words. **CHOSEN**: the bulletin gives the linkage
  register and the table, but not the shape of the calling sequence. The
  shape is MCP's own calling-sequence form (C22-6678-1 p.14), and the
  linkage is STRAP II's (above).
- Each skeleton becomes `(IQS…)DD` text, as p.4 says. **CHOSEN**: one
  80-column card image per skeleton statement, preceded by a word that
  counts the skeleton's cards.
- STRAP statements in the logic portion are assembled as they stand. This
  is the part the host-side `smac.py` cannot run, and the reason for a
  7030 SMAC.

That special library (MBGEN, MEXIT, MBSKL, MEGEN, MMVPT, MOUT, MGETL, the
compares, MOUTF, MOUTV) is `decks/smac_special_library.smac`, written here in
Generator Language with STRAP in its logic. See "The special library" below.
`strap/smac7030_build.py`, a labelled stand-in, still compiles it the first
time, since something has to. **CHOSEN**: each generator is assembled at origin 0, so
every reference inside it is its offset from X1 (p.3, p.13 item 2).

As p.5 says of MEGEN, which "inserts all the SYN cards necessary for branch
table reference", the stand-in ends each generator with the SYNs for the
branch-table symbols it uses. **CHOSEN**: a generator's word 0 is its usage
bit, behind QGUB (p.13: 0 on the generator's first execution), and it is
entered at `1.0($1)`.

## Data in core (all CHOSEN; the bulletin gives no formats)

- **Character code: IQS** (the 89-character set, `strap/charsets.py`).
  p.4 stores skeletons in IQS, and substitution copies subject-statement
  characters into skeleton text unchanged. So both must be in the same
  code. An 80-column card is 80 eight-bit bytes, exactly ten words.
- **Input**: a block of card images, ten words each, ending at a count
  (MEND does not stop the scan, as in `smac.py`). Under MCP this was the System Input or the
  disk (C22-6729 p.9, the COMREC words a processor in the chain receives).
  That path waits for MCP.
- **Output**: card images, ten words each, in an output block, with a
  count in the branch table. A STRAP card that is not a SMAC statement is
  copied unchanged.
- **Parameters**: after a SMAC statement is scanned, a parameter table
  holds, for each parameter (column 1, tag, operation, arguments), its
  first character's bit address and its length. QPT1-QPT5 hold parameter
  numbers in their value fields.
- **The operation table**: two words per operation, for nine characters.
  Word 0 holds characters 1-8; word 1 holds the generator's address as a
  half-word, then character 9.
- **An outer macro's state**: an inner macro (a SMAC statement in a skeleton
  or in generator logic) saves the region SVBEG..SVEND to a stack above the
  deck: pointers, QLIT, QCN, QGUB, X1, X15, X9-X14, the skeleton position,
  the statement text (80 words) and the parameter table (100 words), about
  230 words. p.13 reserves X9-X14 for generator logic but does not say who
  saves them across an inner macro.
- **`/Q/`**: a counter in the shell, "Q0000" upward, one value per generator
  execution (`smac.py`'s CHOSEN C2).
- **QMIBIT and QCIBIT** follow p.13's sentences as read: QMIBIT is one if the
  previous statement was a macro and stays one until the first
  non-continuation card is identified; QCIBIT says the previous source
  statement was a macro. The exact moments they change are **CHOSEN**.
- **Limits of this version, not of the language**: more than 100 parameters
  halts with code 11, and more than 9999 generator executions with code 13.
  The bulletin gives neither. Each failure sets QERRBIT and stops at once,
  where p.13 lets a major error run to the end of the pass.

## The order of work

1. **Done 2026-11-08, with a stand-in.** Generators compile to relocatable
   images. `strap/smac7030_build.py` does this, standing in for p.3's
   special library and p.2's library updating program. It handles MBGEN,
   MEXIT, MOUTF and MOUTV, and refuses the others. Compiling with
   Generator Language generators, as p.3 describes, waits for step 5.
2. **Done 2026-11-08.** The 7030 shell (`decks/smac7030_shell.strap`):
   read a card, classify it, look up the operation, scan the parameters,
   call the generator, copy STRAP cards. It includes the MOUTF and MOUTV
   subroutines and skeleton substitution. Test: `tests/check_smac7030.py`.
   On the model, C22-6678-1 p.47 gives the same 84 output cards as
   `smac.py`, and J28-6128 pp.8-12's MOUTF and MOUTV examples give the
   cards the bulletin prints.
3. **Done 2026-11-08, with the same stand-in.** MMVPT, MOUT, MGETL, the
   compares, `/Q/`, inner macros and continuation cards. Test:
   `tests/check_smac7030.py` part B runs every worked example of pp.5-12
   (72 cards written out by hand from the bulletin), and part C compares
   121 edge-case cards with `smac.py`. Part D runs twelve failures to their
   halt codes.
4. **Done 2026-11-08.** Generators whose logic holds STRAP statements,
   which only the 7030 SMAC can run: part F (16 cards written by hand,
   since `smac.py` refuses these generators). The stand-in passes the STRAP
   through, and expands a SMAC statement found in logic.
5. **Done 2026-11-08.** SMAC compiling generators with the special library
   (p.3). `tests/check_smac7030.py` part H.

## The special library

p.3: the Generator Language statements' generators "are stored on a special
library tape which is called in only when generators are being compiled". The
tape's format and code are lost. `decks/smac_special_library.smac` is written
to what pp.4-11 say each statement does.

**The bootstrap.** Something must compile the library the first time, as
something must have at IBM, and nothing says what did. Here the Python stand-in
does. On the model, SMAC running that library then compiles:

- the library's own source, which must reproduce the library it is running,
  word for word, for all ten generators (eight compare names share one);
- every other generator, which must assemble to the stand-in's image, word for
  word: six MCP generators, one of each shape, plus the bulletin, edge-case,
  `/Q/` and STRAP-in-logic libraries in the suite. `SMAC7030_FULL=1` compiles
  all 78 MCP generators, measured 2026-11-08 at 78 of 78, in 73 minutes.

So the stand-in remains only as the first step of the bootstrap and as a
check. Agreement shows these two compilers agree. It does not show that either
compiles as IBM's library did: the output's form is CHOSEN (see above) and word
equality was the target.

**Skeletons in core and in the output.** p.4 says a skeleton becomes "STRAP Data
Definition statement with IQS entry mode". The stand-in's single 80-character
DD does not fit a card, so MBSKL's generator puts out two 40-character DDs per
statement (**CHOSEN**), which store the same ten words.

**Branch-table entries added, all CHOSEN.** p.2 sends everything through the
table without listing all of it:

| symbol | what |
|---|---|
| QPARM | a parameter's index word, into X9 |
| QPUTC | put out a card as it stands; MBSKL needs this, since `/1/` in a skeleton is text at this point |
| QFAIL | the shell's error halt |
| QINPT | the next input card, which MBSKL reads directly |

**A generator writes into its own skeleton.** No substitution makes a number
from a count, and `MOUT`, `MOUTF`, `MOUTV`, MBSKL and the compares need one, or
the hexadecimal of a compare's characters. Their STRAP logic stores the digits
into the skeleton's text before putting it out. This is p.13 item 6's free
logic, but no page shows a generator doing it.

**Departures from p.1.** p.1 forbids Q in an operation, but p.4 and the errata
print MKPEQ and the like. The printed names stand, exempt in `smac.py`'s check.

**Limits of this version.** Each halts with a code listed in the library's
header: a continuation card in a skeleton (17), a text holding all five end
marks in one 40-character part (18), a count or skeleton past 99 (22). The
stand-in's own checks that N is positive and that a pointer is QPT1-QPT5 are
not repeated: a bad pointer fails when STRAP assembles the generator, and a
negative N is not caught.

## What running it on the model taught

- **`LV` from a `,A` half-word gives a NEGATIVE value.** STRAP prints that
  half-word's last byte as 80 (C22-6678-1 p.48), so bit 24 is set, and bit
  24 of an index word is the value's sign (Reference Manual printed p.19:
  its 25 bits "are interpreted as an address of 24 bits and a sign bit"). A pointer loaded that way walks backward. So MCP's
  arguments are read as `(BU,24)` (C22-6678-1 Appendix A: "All have DDS of
  (BU,24)"), and this program reads its own the same way. Its output
  pointer is an `XW`.
- **A binary VFL multiply's product is at offset 20**, wherever the operand
  came from (Reference Manual printed p.68). The first draft read it at
  offset 0, and the MOUTV example with two non-N sets caught that.
- **SC and LC hold a count in the left 18 bits of the addressed field**, not
  in an index word's count position (bits 28-45), so `LC,$4,STX` on an index
  word loaded its address as a count and ran away. Use `LX` on an index word.
- **The shell found a bug in the model.** An index instruction could run ahead
  of a pending progressive level that was going to write the same register
  (Reference Manual printed p.21: progressive indexing "is executed in two
  parts"). In the frame-restore loop's `ST(BU,64)(V+I),1.0($3)`,
  `KVI,$3,LIMIT`, `BXL,LOOP`, the compare saw the old value, so the loop
  copied one word too many, over the operation table's first word, and every
  macro after an inner macro then missed its lookup. The fix is in
  `bsv/StretchIBox.bsv`, the test is `decks/index_after_progressive.strap`,
  and the record is in `bsv/README.md`.
- **SMAC compiling a generator costs about a minute of Bluesim time.** All 78
  MCP generators took 73 minutes, so the suite compiles six of them.
- **A big image cannot use `gen_tb`'s one-rule `case` loader.** bsc was
  still compiling a 2,200-word image after ten minutes. `FASTLOAD=` loads
  it from a hex file instead.
