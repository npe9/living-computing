## Layering (p04-05)
"SIMPOS is largely divided into two parts -- an operating system part ... and a programming system part ... The
operating system part has three layers -- a kernel for hardware resource management, a supervisor for software
resource management, and i/o medium systems for input/output management." The supervisor is "a collection of
class definitions" (p05), divided into four subparts: object storage (pools), object flow (streams),
execution (processes), environment (directories and worlds). p06: "since PSI does not support virtual memory,
some software supports are necessary to deal with data in file storage."
Execution model (p05): "a system consists of objects and processes ... each process performs operations on
objects, and if necessary, communicates with any other cooperating processes, according to a given program under
a specified environment which keeps global objects."

## ESP conventions stated (p03-04)
Instance predicate `:operation(Object,...) :- ...`; class predicate `:operation(Class,...)` where Class is a class
object or `#<class_name>`; `:new(#<class_name>, Object)` creates; local predicates plain Prolog, callable only in
the class; slot access `Object!<attribute_name>`. Only class/instance predicates are visible outside an object.

## Pools (p06-12) -- interface printed, mostly reimplementable
- as_pool mixin: :add/:remove/:get (p06). sequence -> array (:put_at,:get_at; O(1)) and list (:add_after,
  :add_before,:get_at,:remove_at; removal leaves garbage words) (p07-08).
- index: key = atomic term or string; implemented as hash array (array of lists of key/object entries), standard
  hash function; class 'index' inherits 'array' through 'hash_array' (p08-09). Sparse array = index keyed by
  position (p09).
- bucket: mixin as_bucket inherited first, then a sequence class; path-position [P1,P2,...]; full :get clause
  printed (p10); multi-layer index via path-key [Key1,Key2,...] (p10).
- planned only: bag, set, sorted sequence (p10).
- tap: sequential access, created by :tap(Pool,Tap); generic :get body printed using pool :next/3 (p11-12); "if we
  want a more efficient implementation of a tap, we can define a tap class specific to each pool class" (p12).
- Sketched: hash function unspecified; no slot layout for any pool.

## Streams and IPC (p12-17) -- semantics clear, enough to reimplement at the interface level
- stream: :put/:get; get on empty stream suspends the caller until another process puts; FIFO; shared by many
  processes (p12-13).
- semaphore (p/v via get/put of the atom `token`, :init puts one token; integer semaphore :init(S,Count)) and event
  (:post = put code, :wait = get code) -- bodies printed (p13).
- Mixins planned: priority control, bounded buffer (p14).
- message: sender slot (reply channel), receiver slot, body; mixin as_message provides the first two (p14).
- channel inherits stream: :send/:receive pack/unpack objects into messages; :send_message/:receive_message (p14).
  Messages go to channels, never directly to processes, so a process can receive from several sources (p15).
- port inherits channel (input channel) and holds a list of output channels; :connect adds each port to the
  other's output list; send broadcasts to all connected ports; receive in arrival order (p15-16).
- stream pool: multi-stream get (:get/2, :get/3 returning the stream); channel pool likewise; no send (p16-17).
- source/sink channels wrap i/o-medium operations (keyboard input, screen output) as channels (p17).

## Processes (p17-21) -- state model stated, scheduler only sketched
- Four states: running, ready (in a ready queue), suspended (not in the ready queue; typically waiting on an empty
  stream; made ready by the scheduler), dormant (just created or terminated; unknown to the scheduler; activation
  makes it known). "The dispatcher and the scheduler controls the states of processes." (p18)
- Operations :activate(Process,Program,Goal), :suspend(P,Reason), :resume(P,Reason), :terminate(P) (p18-19).
- Hardware: each process gets a PSI hardware process environment (register set, stack group, heap memory); "The
  architecture of PSI restricts the number of processes in a system to 63"; several are interrupt processes, so
  about 50 ordinary processes (p19).
- Program: a program is an instance of a program class (code shared, data per instance); main program = instance
  predicate, default `goal` (p19-20). Each process has an invocation stack; :invoke(#program,Goal) (class predicate)
  creates a program instance and pushes it on the caller's stack; :activate(Process,#program,Goal) pushes onto the
  target process's stack (p20).
- interrupt_process: trap handlers, device handlers, garbage collector; dispatched by hardware at interrupt/trap.
  Activating one raises a trap; resume on an interrupt process raises a trap, on an ordinary one calls the software
  scheduler; streams need not distinguish (p20-21).
- boot_process: inherits process, overrides create and activate; created/activated by the hardware at bootstrap
  "before the supervisor knows it", then calls those operations itself to come under supervisor control (p21).
- NOT described: priorities, scheduling policy, time slicing, ready-queue discipline, timer (timer: "supports clocks
  and watches", not discussed, p31).

## Environments (p21-26)
- Each process has a program invocation, a library and a directory (p22).
- library: holds classes, retrievable by name -- global environment; class slots also global; example
  :root(#directory,Root_directory) (p22). Class slots cannot be added at runtime.
- directory: index of name->object; :find/:bind/:remove; pathname "Name1>Name2>..." resolved left to right with
  :retrieve (p23). System root directory kept in a class slot of 'directory'; ">Name1>..." = from system root;
  without leading '>' resolved in the calling process's world (p24). :retrieve(#as_global_object,Object,Path).
- world: a sequence of directories with the directory interface; first match wins; shadowing by inserting into an
  earlier directory; working world in an instance slot of the process; :world(#process,World) (p24-25).
- global objects (mixin as_global_object): protection (owner; seals for owner/group/public/super users; classes
  user and group "must be defined"), profile (creation/modification/reference dates), version numbers, mutual
  exclusion by a per-object lock stream -- "The actual implementation of these facilities is still under
  consideration" (p26-27). Sketch only.

## Permanent objects (p27-28) -- sketch; code is in TR-059 p22
as_permanent_object mixin: instance file as class attribute, record pointer as instance attribute; each class
defines its own conversion predicates. Instance file = table file of fixed-length records. Record pointer = file
identifier (file number on disk / file object in memory) + file marker. Directory file maps names to record
pointers (:find). Permanent directory = in-memory cache of a directory file; bind it into the system tree to reach
permanent objects by pathname.

## Remote objects (p28-31) -- design sketch (superseded by ROAM, TR-283; not in F2 scope)
Remote object id = (node object, object number); per-node object table maintained by the network manager;
operation encoded as message (operation identifier string, object number, parameters) to the local network manager,
forwarded to the remote one. Mixins as_remote_object (encode+send) and as_pervasive_object (decode+execute).
Remote directory (remote system root has object number 1); remote channel (send only).
