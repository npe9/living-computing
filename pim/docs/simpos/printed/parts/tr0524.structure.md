# TR-524 — The SIMPOS Distributed File System: Its Design and Implementation (K. Yoshida, Nov. 1989)

Citations are PDF page (pNN) / printed folio (fNN). All 38 pages were read: OCR text in full,
every page by eye on contact sheets, and the code and table pages from 300 dpi crops. "INFERENCE" marks
anything not stated in the report.

## Context stated
- The PSI-I and PSI-II machines run SIMPOS. The whole of SIMPOS, "from the user interface to the kernel and device handlers, is written in ESP" (p3/f2).
- More than 300 PSI machines are on LANs/WANs. Two protocols are available: PSI-NET and TCP/IP, the latter from spring 1989 (p2-3).
- The distributed file system has been in operation since summer 1987 (p6/f5).
- SIMPOS introduces dynamic objects. `class process` creates process instances, each holding an activation record. The kernel schedules processes non-preemptively, not by time slicing (p8/f7).
- PSI-I limits process creation to 63 processes (p11/f10).
- PSI-II costs are about 30 µs per inference. A process switch costs 1 ms, symbol retrieval 0.35 ms and class retrieval 3.24 ms (p29/f28). Table 3 (p36) gives 3.25 ms for class retrieval.

## File system history (p4-6)
1. 1984: a semaphore-based local file system. The storage structure is a UNIX-like hierarchical tree of expandable files. Lock and unlock are done by user processes.
2. 1985: redesigned around a "dynamic object" (a process encapsulating a resource, monitor-like, using message passing) [ref 46 = TR-108, in Japanese].
3. 1986: a capability/password protection mechanism was added.
4. 1987: ROAM [ref 47] was embedded and every file and directory method reimplemented on it. User names and pathnames were globalized. Compatibility was kept by "reconstructing, renewing or newly defining super classes of the existing classes" (p6).

## Storage management (p8-10) — sketched, not reimplementable
- Volumes are physically 1 KB pages. The allocation block is 4 pages; it was 1 page originally, changed because about 50% of files are under 4 KB (p9, footnote).
- Files are expandable, with no size given at creation.
- There are three file types: **binary files** ("which are text files"), **table files** (fixed-length records) and **permanent object files** ("frozen images of objects in main memory", compared to Apollo typed files) (p9).
- Each file has a numeric identifier, like an i-node number, and one or more names in a tree. The top is the root directory.
- A file name is identifier.extension.version, e.g. `humm.txt.3`. Local pathname: `>sys>user>gee>humm.txt.3`, where the first `>` is the local root (p9).
- Versions: the file system assigns the version and increments it on each new creation. Opening without a version gets the latest version. Version content is mutable, and versions are kept until explicitly purged (p9).
- **World** is a set of aliases. An alias can name any pathname, e.g. `snoopy` = `>sys>user>gee` makes `snoopy:humm.txt` valid (p9). A remote alias such as `snoopy` = `icpsi200::>sys>user>gee` also works (p22/f21).
- **On-close writing.** Main memory and I/O devices transfer through I/O bus memory. A fixed partition is the disk handler's cache, with LRU management. The i-node table and free-block map are accumulated in main memory, written to the cache at each close, and the cache is then written back to disk (p9-10). Table 1 (p34) calls this policy "Write-through, on close (local cache)".
- Disk I/O costs 4 process switches per operation: user, then file manager, then device handler, and back. That is at least 4 ms (p29/f28).
- **Not given:** the on-disk layout, i-node format, directory entry format, free-map format and volume label.

## Global naming (p10/f9)
- Users are identified locally by login name. There are no user groups; passwords are used instead.
- A global name is `<HostName>::<LocalName>`, e.g. `icpsi200::>sys>user>gee>humm.txt` (p18). The host name identifies a machine, not a location.
- There is no remote mount and no global name service (p22).

## Concurrency control (p10-15) — detailed enough to reimplement the semantics
- **Logical and physical objects.** Every shared resource (file, directory, volume) has one physical object and one or more logical objects (p10-11).
- The ideal design is one dynamic object per physical object (Fig. 1a). In practice all of them are fused into one **file manager process** (Fig. 1b), and their channels are merged into one (Fig. 1c) (p10-11).
- Fig. 2 (p11, poor scan) gives the network view: logical files lfNN, physical files pfN and processes PN at sites icpsi100 and icpsi200.
- **Session.** A session runs from `:open` or `:make` on a file interface class object (`#binary_file`, `#table_file`) to `:close` on the logical file. Operations in between include read, write and add (p11).
- **Asynchronous primitives** (p12):
  - `submit` sends a request without blocking, `wait` waits for the reply, and `probe` tests whether a reply has arrived. A message identifier pairs requests with replies.
  - Each I/O operation has a synchronous and an asynchronous form (`:add` / `:submit_add`); the synchronous form is submit followed by wait.
  - Using the asynchronous form for double buffering gave about 20% improvement.
- **Buffer and marker** (p12):
  - Every I/O operation takes a buffer (variable length) and a marker (access position).
  - `read` and `write` are random access at the marker. `add` is sequential, and its position is kept by the physical file.
  - A logical file contains an internal **accessor** (a buffer+marker pair), and external accessors can be attached to it. References to the buffer and marker, not their contents, are passed to the physical file.
- **Open modes** (p13-14):
  - `exclusive`: allowed only when the physical file is closed; read and write.
  - `input`: allowed when closed or open for input; reads only.
  - `output`: allowed when closed or open shared; read and write, and suppresses writes from shared-mode logical files.
  - `shared`: allowed when closed, shared or output; read and write, subject to suppression.
  - Suppressions are released at close.
- **Request modes** (p14): `suppress` waits until released; `immediate` withdraws the request.
- **Message management** (p15):
  - Each physical object has a FIFO message queue of suppressed requests. The file manager is "just a scheduler of physical objects": it delivers each message from a logical object to its physical object.
  - There are two priority levels, `normal` and `express`. Express messages execute immediately.
  - A normal message is executed if acceptable. Otherwise it is queued (suppress) or answered with a withdrawal reply (immediate). Once anything is queued, later requests queue behind it even if acceptable.
  - When a process aborts, each of its logical files sends an express abort message. The physical file then cleans up that file's queued requests and its suppressions.
- **Consistency** (p23):
  - input, output and exclusive opens give session semantics;
  - read and write in shared opens give time-dependent semantics;
  - add in shared opens gives UNIX semantics, since only the physical file keeps the position.
- Worked example (p12-14): "To be, or not to be. That is the question!", with three possible interleavings printed on p14.

## Access control (p15-18) — detailed enough to reimplement
- **Password holder.** A user has up to 10 passwords of at most 16 characters each, plus an implicit default password. A process gets a copy at initiation and may modify it (p16).
- **Rank.** The permanent ranks are `super_U` (whole network universe), `super_A` (resident area), `super_N` (resident site) and `general`. Super users drop to general outside their region. The temporary rank, super or general, is the **user mode** (p16-17).
- **Directory entry protection.** Each entry has a network publicity, `g` (global) or `l` (local), and an access list of tuples <Password, ControlRight, AccessRight> (p17):
  - The access list can hold the meta password `$owner` (the owner's globally unique login name), up to 3 user-defined passwords, and the default password.
  - Control rights: `f` find, `d` delete/rename, `m` modify rights, `a` append passwords.
  - Access rights: `r` read/look up, `w` overwrite or delete entries, `a` append data or register entries.
- **Algorithm.** At every directory entry on the path: (1) publicity check; (2) if the rank is super, grant full capability; (3) check the access list and sum the capabilities of all accepted passwords into the **original capability**. The open mode then limits it to the **current capability** (e.g. input removes w and a) (p17-18).
- In the implementation, physical directory objects under the file manager do these checks, and no logical object is created per entry (p18).
- Each operation on a logical object is checked against the current capability (p18).
- Fig. 3 (p13) gives a concrete access list (transcribed in listings/tr0524_p13.esp): `$owner fdma rwa`, `olive f rwa`, `popeye f r`, `default none none`.

## Communication control: ROAM (p18-21, Fig. 4 p20)
- ROAM sits on top of the session layer of the SIMPOS network system (p18).
- **Reflection.** For each client process, one server process is created at each remote site it accesses. The local stand-in object is the **proxy** and the remote one the **original**. Both have the same class, and each knows which it is. A proxy forwards every operation (p19).
- **Message management.** Messages are packed in tagged representation into fixed-length packets. They can be of any length and hold data of any type and binding direction. Extra information can be added (p19).
- **Line management.** A virtual circuit is set up on the first access, and user information is sent then. It is cut when either end terminates (p19).
- **Object management.** ROAM handles export and import, propagates references, and supports nested remote calls (p19).
- **Interface:**
  - Inherit `remote_object` (complete global object) or `as_remote_object` (incomplete global object, which travels only as an argument and whose state can be frozen into the extra information).
  - For each method, define an external method that calls `:g_call`, which issues `:r_call` for a proxy or `:l_call` for an original. On the remote side the server process calls `:x_call` on the original, which calls `:l_call` (p20-21).
  - Fig. 4 (p20) shows `:read_data` → `:read/2` → `:read/4` → `:g_call` → (`:l_call` → `:send_receive` → `:submit`/`:wait` → file manager) or (`:r_call` → network manager → network manager → `:x_call` → `:l_call` → ...).
- In the file system, only logical files and directories are complete global objects. Buffers and markers are incomplete global objects, and buffer data rides in the request of output operations and the reply of input operations (p21). See Appendix A, listings tr0524_p37/p38.
- **Protocol choice.** Each logical object's ROAM checks which protocol exists between the nodes. PSI-NET is preferred if both exist (p24/f23).
- The network layer is virtual circuits. There is one export/import table **per process**, collected by the ordinary GC when the process ends. There is no global GC and no object migration (p25, p27).
- Table 2 (p35): GOID = `[node#, creationtime]`, "given to an object at its first exportation", and locally a direct pointer. TR-283 gives GOID as node name + exporting time + process number. This is a VARIANT between the two reports.
- Table 2 (p35) also states: local GC is mark-and-sweep; class compatibility across nodes is "Not guaranteed. User's responsibility"; security is "Authentication but no encryption in ROAM".
- Packets are 4200 bytes because of PSI-NET, and a 1024-byte version was being tested. A null RMC took 471 ms (current) and 207 ms (new) (p28).

## Code size (p24/f23)
- Network transparency added 2.7K lines of ESP, about 10% of the previous local file system. TR-283 p10 gives 25.5K lines for the entire file system.
