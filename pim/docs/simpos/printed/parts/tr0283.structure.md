# TR-283 — Remote Object Accessing Mechanism in SIMPOS: Its Design and Application (K. Yoshida, June 1987)

Citations are PDF page (pNN) / printed folio (fNN). All 21 pages were read: OCR text in full, every page
by eye on a contact sheet, and pp16-21 (figures, tables, appendices) from 300 dpi crops.
"INFERENCE" marks anything not stated in the report.

## Context
- "All of the modules constituting SIMPOS, including the kernel layer such as device handlers, are written in ... ESP" (p3/f1).
- About 100 PSI machines are connected by 10 Mb Ethernet (LAN) and DDX (global network) (p3).
- SIMPOS separates objects from processes. General objects encapsulate data and operations, and the execution environment is held by process objects (p4/f2).

## ROAM design (section 2)
- **Original and proxy** (p4):
  - The original and its proxies have the same class and the same structure. The only difference is the slot `object_category`, which is `original` or `proxy`.
  - An object accessible over the network is a **global object**.
- **Client, server and controller** (p4-5):
  - One server process is created per client process per remote node.
  - Each node has one **controller process**, which creates and terminates server processes at that node. A client's first access to a node asks the remote controller for a server.
  - When the client ends, it asks the controllers to kill its servers. Calls are synchronous.
- **Line management** (p5):
  - Each process holds virtual line objects keyed by node name: one from its client and the others to its servers. Any process can be both server and client.
  - A virtual line is "an external stream with the synchronization function", provided by the underlying communication system.
  - On every remote call, the process checks whether it already holds the line, i.e. whether its server exists.
- **Classes across nodes** (p5):
  - There is no metaclass in ESP. The **library subsystem** manages all class objects.
  - A **package** is a set of classes. Within a node, a class is identified by its **class complete name** = (package name, class name).
  - ROAM treats classes with the same complete name on different nodes as identical, and the user must set up the library to match. On export, the complete name is sent; on import, the class is retrieved from the local library.
- **Instances** (p6):
  - SIMPOS instances have no implicit object identifiers. On first export ROAM assigns a **GOID** = (resident node name, exporting time, process number), and proxies carry it.
  - Each process holds one **export table** and one **import table**. Importing an unknown GOID creates a proxy from the class complete name and enters it in the import table.
  - Fig. 1 (p16) and Fig. 3 (p17) show GOIDs written as `N2T1P21`.
- **Messages** (p6-7):
  - There are request and reply messages, variable length and free format, each with three fields:
    - **control**: type plus **GMID**, the global message identifier;
    - **standard**: method name, target and parameters, or status and parameters;
    - **extra**: user-definable.
  - Messages are carried in fixed-length unit packets taken from a reused packet pool. Each packet has a data field and a control field holding a sequence number.
  - Data elements use a tagged representation.
- **The tag table and message layout are PRINTED in Appendix 2 (p20-21), transcribed in listings/tr0283_p20.esp.** This is the most concrete wire-format material in the two reports. It fixes:
  - message type codes X'0010 (request) and X'0020 (reply);
  - tag values: undefined variable X'FFFF; integer X'0010; atom X'0030 (sent as a string); string X'000#/X'0F0#; heap vector X'0060/X'0F60; list X'0070; stack vector X'0080/X'0F80; class object X'FF10 (class name string); exported instance X'FF20 and imported instance X'FF30 (class name string + GOID).
  - Short and long forms are given, but how they differ is not stated, nor the field widths or byte order.
- **Call sequence** (p7):
  1. The proxy packs the request and sends it, and the client waits.
  2. The server finds the original by the destination information.
  3. The original unpacks the message, calls the method on itself, and packs status and results.
  4. The proxy unpacks the reply and unifies it with the original call pattern.
- **Nested calls** (p7, Fig. 2 p17):
  - Replies are matched to requests by GMID.
  - A process waiting for a reply that receives a *request* instead serves it, as a server would, then resumes waiting.
- **Object migration** (p8, Fig. 3):
  - Proxies created at further nodes share the GOID. The original is searched for by GOID.
  - Tables are per process, so the search fails if the original's process has died.
- **Errors** (p8): each process holds a **status object** recording the execution status of its last method call. The status is asked of the process, not the object.
- **Customization** (p8-9):
  - The extra field is used, for example, to send slot values ahead and avoid nested calls.
  - Complete objects can make remote calls. Incomplete objects only travel as parameters, with their state frozen into the extra field.
  - User-redefinable methods are of three kinds: the proxy-creating method, the freeze/melt methods, and the extra-field handlers. No names are given.
- **Implementation** (p9): the first version is 16 classes in about 2200 lines of ESP, in four groups: remote object kernel classes, message classes, process-related classes, and others. Only `remote_object` and `as_remote_object` are named.
- **User interface** (p9):
  - Inherit `remote_object` (complete) or `as_remote_object` (incomplete); `as_remote_object` is inherited by `remote_object`.
  - Define external methods that call `:g_call`, plus the corresponding `:l_call` bodies. `:g_call` makes `:r_call` or `:l_call` depending on the object category.

## Global file system (section 3, p10)
- The local file system had dynamically expandable resources, a hierarchical directory tree, a current directory, and logical names (aliases). It assumed cooperative processes [Reid83].
- The global system makes the name space a global tree whose subtrees are the local trees. An absolute name is the node name concatenated with the local pathname.
- Files and directories are complete objects. Buffers and position markers are incomplete objects.
- The change was 2.7K lines of ESP, about 10% of the whole 25.5K-line file system.

## Communication layering (section 4, p10-11)
- There are three process levels: user-user (ROAM), manager-manager, and handler-handler (the session layer). Below the transport layer, a hardware controller **LIA/LIB** connects to Ethernet.
- Measured costs (Tables 1-4, p18): 640-680 ms per RMC, against Flamingo's about 11 ms.
- Planned fixes:
  - packets of 1400 bytes instead of 4200;
  - a ROAM-specific communication system that avoids buffer copies (the existing system "accepts buffers, not messages");
  - a library cache, since message interpretation costs 100-140 ms, mostly in class retrieval and atom/string conversion.

## Discussion (p11-12)
- There is no global GC. Local GC is "an exhausted GC based on the mark and sweep method".
- The built-in predicate `method_call` does not handle remote calls, because ROAM is a layer above the basic method-call mechanism (p12).
- Planned future work: declare global objects as mobile or fixed, with a per-node table for mobile objects.
