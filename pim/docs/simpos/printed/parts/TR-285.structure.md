# TR-285 Programming in ESP -- Experiences with SIMPOS (T. Chikayama, Jul 1987). 15 PDF pages (folio = PDF-3); OCR read in full (pp2-13); no listing. Prose with reimplementation-relevant facts:

- Versions (p5): FGCS'84 demo (Nov 1984; no self compiler); 0.7 first stand-alone end 1984; 1.0 spring 1985; 2.0 spring 1986; 2.5 July 1986. Newest: ~230,000 source lines, 1,400 classes, 18,000 predicates.
- KL0 control features (p5-6): exception (built-in error invokes a handler predicate that may return to continue), bind-hook (freeze), multiple-level cut (catch/throw), persistent alternatives (never removed by cut); low-level resource manipulation; Lisp-like impure database updates; strings.
- ESP semantics (p6-7): local predicates statically bound (name/arity, class scope); methods dynamically bound on the first argument's axiom set; slots updated by side effect; one class object per class, identified by class name; instances anonymous; superclass union of axioms with a strictly defined order; cut gives overriding; demon combination (before/after conjunction) as in Flavors.
- Implementation (p8): method lookup by name and arity at runtime; slots accessed by name; inheritance analysed at linkage time so lookup is a hash search; firmware built-ins for method invocation and slot access (~30% overhead vs array index / local call). KL0 interpreter in microcode, structure sharing, ~30 KLIPS average.
- Situation mechanism (p10): events looked up in the process's situation stack; choices: resume (after recovery), fail the operation, go back to a resumption point recorded in the stack (e.g. top-level loop), or kill the process; may be decided conversationally. Built-in exceptions raise events; catch/throw via multi-level cut; situation stack kept consistent with persistent alternatives. bind_hook unused in SIMPOS. SKETCHED but the control semantics are concrete.
- I/O by polymorphism (p11): the unparser calls :putc on whatever destination object (file, window, counter object). Process termination cleanup: the process management module calls the same method on each held resource object (files, semaphores, network connections). INFERENCE: a process holds a list of resource objects (cf. TM-100 "resources" slot).
- Windows (p12): applications inherit several SIMPOS window classes to mix functions.
