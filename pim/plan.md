# PIM/m reproduction plan

## Scope

Reproduce one PIM/m processing element first, then its communication
hardware and a small deterministic mesh. "PIM" is ambiguous today with
processing-in-memory; here it always means ICOT's *Parallel Inference
Machine*. The four other PIM variants are not silently blended into the
PIM/m model.

The target is an instruction- and cycle-accounted Bluespec model able
to run surviving PIM/m machine code or microcode and, eventually, a
documented KL1 workload. If no bit-exact executable survives, the first
software oracle will be a manually assembled diagnostic derived from a
primary manual and explicitly labelled manual-derived.

## Historical accuracy rule

The Bluespec model must reproduce the original PIM/m hardware block
diagram and the descriptions in the primary sources. It is a
historically accurate architectural reproduction, not an FPGA emulator:
do not invent, simplify, or reorder structure for FPGA convenience.
Every module, pipeline stage, bus, and control signal must trace to a
block diagram, manual page, or technical report. Where the evidence is
silent, mark the structure unknown rather than filling it with a
plausible FPGA design. FPGA synthesis is a downstream check, not the
definition of the architecture.

## Evidence gates

1. Acquire local, checksummed copies of the 1992 ICOT proceedings,
   TR-324, PIM/m hardware and microprogramming documents, PIMOS/KL1
   documents, and any surviving listings or binaries. Record stable
   archive locations, printed-page mappings, and provenance.
2. Build an architectural inventory: word and tag formats, registers,
   instruction and microinstruction encodings, traps, memory system,
   mesh packets, routing, scheduling, and every published latency.
   Mark every field as confirmed, conflicting, or unknown.
3. Locate an independent encoding oracle. Prefer a printed listing with
   machine-code columns, then an original assembler or binary. Do not
   infer encodings from prose examples or from a later PIM variant.
4. Decide whether the surviving evidence supports cycle accuracy. If it
   does not, implement only documented transitions and report timing as
   unknown rather than borrowing it from Multi-PSI or another PIM.

## Staged implementation

1. Write a table-driven assembler/disassembler with round-trip and
   negative tests. Every opcode entry cites a document and printed page.
2. Model tagged words, the local store, register state, and fetch/decode.
   Unknown and reserved encodings stop loudly.
3. Split the processing element into Bluespec pipeline/state-machine
   modules. Arithmetic, unification, goal control, and microcode control
   get request/response interfaces where the documents describe
   multi-cycle operation.
4. Add interrupts, faults, and the documented interface to PIMOS. Run a
   single-PE diagnostic before introducing nondeterminism or a network.
5. Model a mesh link and packet flow control, prove it with two PEs, then
   build a parameterized small mesh with deterministic arbitration and
   deadlock-directed tests.
6. Add KL1 only through a documented compiler/runtime path. Preserve the
   distinction between architectural tests, runtime tests, and language
   benchmarks.

## Definition of the first milestone

The source inventory is checked in; an encoding table covers every
documented PIM/m instruction and identifies every gap; an assembler
round-trips a primary-source example; and a one-PE Bluesim smoke test
fetches, executes, and halts on that example. The full repository test
suite remains green.

   **Bluesim boot milestones.** The user's directive is to run PIMOS in
   Bluesim, using the original binaries as the driver. The sequence:

   1. **Decoder.** Complete `asm/unlsav.py`: walk all 42 modules of
      `pimm_kernel360E.sav` (GC terms, predicate table, code area),
      disassemble each module's code, and verify the module boundaries
      against `0xFFFF`.
   2. **KL1-B execution design.** Decide new module vs. extending the
      diagnostic ISA; record the register set (`HP`, `SR`, `SSP`,
      `RQFP`/`CRFP`/`SRFP`/`SSFP`, `Carg`, tag mask), the 40-bit tagged
      word, and the fetch/decode/execute split in this plan before code.
   3. **Interpreter module.** Fetch/decode/execute over
      `docs/kl1_encoding.md`; start with a hand-assembled program and
      the kernel's `set_value`/`get_bound_value` sequences.
   4. **Device shims.** The IPL loads `.sav` modules over SCSI. Two
      tiers: (A) bootstrap — preload the decoded `.sav` images into
      SDRAM/BRAM at their load addresses and start the IPL, bypassing
      the fetch; (B) target — a direct-access block device implementing
      the DAM command set (INQUIRY device code 0, TEST UNIT READY,
      READ(6), WRITE(6), MODE SENSE, READ CAPACITY) backed by a file or
      the ULX3S SD card, so the unmodified IPL fetches the modules.
      Block size is reported by READ CAPACITY / MODE SENSE, not chosen
      by the shim. The full FEP protocol at unit 7, LUN 0/1 is only if
      the protocol itself is the goal. Add the console the boot log
      needs.
   5. **Boot-log oracle.** The manual gives the successful sequence
      "Link Modules ... / PIMOS booting ... / V 3.000 ... / SCSI UNITS
      FOUND". A Bluesim boot that reproduces it is the acceptance test.

   **KL1-B execution design (milestone 2).** The model's current ISA is
   the diagnostic stand-in; KL1-B is a separate execution path. The
   design, recorded before code:

   - **Module.** A new `PimKL1B` module with a request/response memory
     interface and a `step()` clock enable, alongside `PimPU`; do not
     overwrite the diagnostic ISA, which the smoke and negative tests
     depend on.
   - **Word.** 40-bit tagged word: 8-bit tag + 32-bit data, matching
     TR-389 p. 9 and the `.kbn` heap image. The tag values are the
     model's, not historical.
   - **Registers.** `PC`, the argument registers `Carg`/`argregN`, `SR`,
     `HP`, `SSP`, `write_mode`, and the four free-list pointers
     `RQFP`/`CRFP`/`SRFP`/`SSFP` (TR-246 p. 4), plus a tag mask register
     for the macro-call conditions (TR-389 p. 7).
   - **Memory and tags.** The 40-bit word is 8-bit tag + 32-bit value.
     Tags in use in the model: `0x23` instruction/code, `0x01` variable
     (UREF), `0x02` integer. The heap is a flat cell array with `HP` as
     the next free cell: `write_value` stores a register at `HP` and
     advances it; `get_bound_value` reads the cell a register points
     to. Structures are consecutive heap cells with a list/structure
     tag and a pointer, per TR-246 p. 3. The tag values are the
     model's, not historical, and are fixed here so later instructions
     conform rather than inventing per-instruction tags.
   - **Goal records.** A goal record is `{Narg, argregN, code address,
     next}` (TR-246 p. 3). The ready queue is a linked list of records,
     with `RQFP` at the head and `CRFP` the free list. `execute`
     allocates a record, fills its arguments, and jumps to the code
     address; `proceed` pops the next record and jumps to it; `suspend`
     hooks the current goal onto the variables it blocked on and returns
     to the ready queue. Suspension records and suspension flag records
     use `SRFP`/`SSFP` (TR-246 p. 3-4). The model uses a fixed pool of
     records (a small power of two) rather than the documented free-list
     discipline; the pool size is a model choice, not historical.
   - **Dereference and suspension.** `deref(w)` follows `REF` cells
     (tag `0x03`) through the heap until it reaches a non-REF; `UREF`
     (tag `0x01`) is an unbound variable. Every `wait_*`/`read_*`/
     `get_*`/`unify_*` instruction shares this deref. Binding a `UREF`
     writes the bound value into its cell and resumes the goals hooked
     on it. `suspend` adds the current goal record to the variable's
     suspension list and returns to the ready queue; the model keeps a
     per-variable suspension list (a small table) and resumes by
     enqueueing the hooked records. The deref depth and the table size
     are model choices.
   - **Multi-word instructions.** The c40 family (set/put/get/write/
     read/wait_constant) is two words: the opcode/register word, then
     the 40-bit constant. The fetch reads the second word and advances
     PC by two for those opcodes. The split is fixed here so each
     instruction does not re-decide it.
   - **Decode.** Opcode = bits 31–24 of the value; operand fields per
     `docs/kl1_encoding.md` (`r`, `r_r`, `r_r_r`, `c8`, `c16`, `c24`,
     `c8_r`, `r_c16`, `atom`, and the address-dependent types).
   - **Stages.** Fetch/decode from memory, execute one instruction per
     rule, with the atom special cases (`0x23xx` + atom name) handled in
     decode. No pipeline claim until the model is tested.
   - **First test.** A hand-assembled KL1-B program exercising
     `set_value`/`get_bound_value`/`write_value` and `proceed`, run in
     Bluesim, with the same injection discipline as the existing
     testbenches.
