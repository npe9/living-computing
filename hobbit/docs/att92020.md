# ATT92020 against ATT92010

The Hobbit BeBox prototype's software is about to run on our Hobbit
models, and the models follow the ATT92010.  This document establishes how
the ATT92020 differs, what Be's own kernels show about which part they
ran on, and what the reference model (`sem/hobbit_sem.py`) now does when
asked to be a 92020.

## Summary

- **No AT&T document for the 92020 has been found**: no data sheet, no
  programmer's reference or supplement, no errata (`att92020/MANIFEST.md`,
  "Not found").  Every 92020 fact below is secondary: contemporaneous
  trade press, AT&T's press release as reprinted, or Be's 1994 kernels
  read as data.
- The press calls the 92020S **binary- and pin-compatible** with the
  92010.  Two differences visible to software are named in print: a
  **prefetch buffer doubled from 3K to 6K**, and a new **Wait For
  Interrupt** instruction.  The second has no published encoding.
- **Be's kernels** (March and November 1994) read the ID register and
  compare it with **`0x0E33D03B`**.  Only if it matches do they print
  "Running on Hobbit 020 processor" and install a workaround for
  **FLUSHPBE**.  The workaround makes bit 10 of FLUSHPBE's own address
  depend on bit 10 of the flushed address.  November keeps them equal;
  March keeps them opposite.  Neither kernel uses an instruction that the 92010
  lacks.
- **Was the BeBox a 92020 machine?** Be's own hardware documentation
  says it was designed around the 92010.  The introduction, rev. 9/15/93,
  "CONFIDENTIAL: Be Labs" (`hobbit/build/bebox/docscans/intro1.jpg`,
  held off git by the BeBox agent's `docs/bebox/MANIFEST.md`), says: "two
  25 MHz CPU's (ATT 92010 "Hobbit" chips) and three 50 MHz DSP's".
  - That draft predates the 92020's announcement (18 Oct 1993, volume
    1Q94; MPR 7:14 Table 1).
  - It is backed by an OSNews report of an eBay unit ("ATT92010") and
    by the johnrash/bebox emulator notes.
  - The 1994 kernels handle both parts.  Their "020" message is printed
    only on an ID match, so the string in the binary does not show that
    any machine had 92020s.  Whether some boards were later fitted with
    the pin-compatible 92020S is not known.  The kernels' 020 code
    suggests Be at least tested one.
- **The model**: `State.part = "92020S"` (CLI `--part 92020S`) answers
  the ID register with `0x0E33D03B`.  Everything a source leaves open is
  refused (`Unsourced92020`).  The default stays `"92010"`.

Grading used below:

- **P** = primary (an AT&T manual for the part).
- **V** = vendor secondary (AT&T's press release as reprinted).
- **T** = trade press of 1993-94.
- **B** = Be's kernels, read as data.
- **M** = modern secondary.

## Differences

ATT92010 cites are the PRM (`ATT92010_Hobbit_Programmers_Reference_Jan93.pdf`,
printed page; PDF page = printed + 8 in Chapter 1, + 58 in Chapter 3) and the
data sheet (`ATT92010_Hobbit_Microprocessor_Data_Sheet_Dec92.pdf`, page
= PDF page).  92020 cites are in `att92020/MANIFEST.md`.

## Be's kernels

The BeBox software agent fetched Be's binaries to
`hobbit/build/bebox/` (branch `worktree-agent-aeb73561b39e2ec97`, commit
8315ce07, `hobbit/docs/bebox/MANIFEST.md`).  They were read here as data
and never executed.  A throwaway ELF reader drove
`asm/hobbit_asm.py`'s disassembler; the kernels are unstripped, so the
names below are Be's.  "Mar" is `Hobbit-9308000044.kernel`, built 1 Mar
1994; "Nov" is `hobbit-9308000058.kernel`, built 23 Nov 1994, which is
identical to `hobbit-930800009`.  The stripped `installer.kernel`
has a byte-identical `.text`.

### Identification (both kernels)

```
_get_id:          CPU; MOV %ID,R4; RETURN R0              (Nov 080c0590)
_main1:  ...      CALL _get_id
                  CMPEQ $0x0e33d03b,R4                   (Nov 080c12ec, Mar 0820d1e6)
                  JMPFN past the block
                  printf("Running on Hobbit 020 processor\n")
                  R4 = _get_id(); MOV R4,*$0x8000190
                  MOV &_flushpbe_020,_flushpbe_vector
                  if (&_pbe_off & 0x400) or !(&_pbe_on & 0x400):
                      printf("020 processor: flushpbe code has moved - fix it!!\n"); JMP .
```

- `_flushpbe_vector` starts as `_flushpbe_ok`, a plain `FLUSHPBE R4`
  (Nov: the word at 0x080e0630 is 0x080c0118).
- The kernel has no other ID constant.  `0x1000003B` (the 92010, mask
  two) appears in neither kernel, so the johnrash/bebox note that the
  machine's ID register reads `0x1000003b` is the emulator's choice.
  Neither kernel can confirm it.
- The 92010 path is simply "not `0x0E33D03B`".

### The FLUSHPBE workaround

```
_flushpbe:        JMP **_flushpbe_vector
_flushpbe_ok:     FLUSHPBE R4 ; RETURN R0
_flushpbe_020:    ENTER R-16
                  [Mar only: MOV R20,*$0x8000190]
                  SHL3 $21,R20          ; accumulator R4 = target << 21
                  CMPGT $0,R4           ; F = target bit 10 set (p. 3-13: src1 > src2)
                  Nov: JMPTY _flushpbe_on   Mar: JMPFY _flushpbe_on
                  FLUSHPBE R20          ; Nov 080c012c / Mar 08200136: bit 10 clear
_pbe_off:         RETURN R16
_flushpbe_on:     FLUSHPBE R20          ; Nov 080c0766 / Mar 0820075e: bit 10 set
_pbe_on:          RETURN R16
```

- **November kernel**: a target with bit 10 set is flushed from the copy
  whose own address has bit 10 set, and a target with bit 10 clear from
  the copy with bit 10 clear.  The instruction's address and the target
  agree in bit 10.
- **March kernel**: the branch is inverted (`JMPFY` against `JMPTY`, with
  the same `CMPGT`), so the two always *disagree* in bit 10.
- Both kernels check the same placement (`_pbe_off` with bit 10 clear,
  `_pbe_on` with bit 10 set).  Those are the RETURNs after each FLUSHPBE,
  and each has the same bit 10 as its FLUSHPBE.  So the rule changed
  between March and November, or one of the two builds is wrong.
- **What is established**: on the 020, FLUSHPBE depends on bit 10 of its
  own address.  **The sense is disputed** between Be's two builds.  No
  third kernel settles it: the third surviving disk (`hobbit-930800009`)
  carries the November kernel byte for byte, and `x-boot`'s
  `boot`/`bootp` and the update archive contain no ID compare.
- **The model follows the later kernel**: a disagreeing FLUSHPBE is
  refused, and an agreeing one is the 92010's no-op.  The model tests the
  FLUSHPBE's own address; Be's placement check tests the RETURN after
  it, which has the same bit 10 in Be's code.
  - Under `--part 92020S`, the November kernel's FLUSHPBEs retire.
  - The March kernel's 020 path, Be's own workaround of that date, is
    refused at its first FLUSHPBE.  That is a refusal, not a claim that
    March was wrong.
- **Interpretation, not a source**: a 6K three-way buffer has 2K ways,
  one index bit more than the 92010's 1K ways (3K, three-way), and that
  extra bit is address bit 10.  Two explanations fit equally well:
  - the 92020 took index bit 10 from the FLUSHPBE's fetch address,
    which needs November's pairing;
  - it took the inverse, or the line the instruction itself occupies,
    which needs March's.

  No AT&T document says which.
- **The operand**: `SHL3 $21,R20` does not change the operand.  It
  writes `target << 21` to the accumulator R4 ("For SHL3, the result is
  placed in the accumulator", PRM p. 3-41), and `CMPGT` tests that
  value's sign, which is the target's bit 10.  `FLUSHPBE R20` then names
  the word held in R20.
  - **The manual agrees**: Table 3-2 (PRM p. 3-4, read from the page
    image) defines `word32` as "A 32-bit value with any of the four
    word operand addressing modes (modes >= 0xC)", and FLUSHPBE
    invalidates "the quad-word at src" (p. 3-26).  So in mode 0xD, src
    is the word stored at SP+20, and that word is the address flushed.
  - **The model's general rule differs**: `_word32_value`, which
    `CATCH`, `ENTER` and `FLUSHPTE` share, reads mode 0xD as the slot's
    address SP+20.  That is right for CATCH/ENTER, whose printed loops
    take the stack offset as the new MSP (pp. 3-10, 3-19), but it is
    not Table 3-2's plain reading.  The 92020S check reads the word, as
    Table 3-2 and Be both do.  For the 92010 the difference cannot be
    seen, because the model's FLUSHPBE is a no-op.
  - **Mode 0xE (`FLUSHPBE *R4`) is ambiguous**:
    - Table 3-2's value reading gives the word the pointer points at.
    - FLUSHPTE's note on p. 3-27 reads the same mode as the pointer
      itself: "the address is moved into the stack cache and the stack
      offset indirect addressing mode is used".  Be's `_flushpte`
      (`FLUSHPTE *R4`) fits that reading.
    - So under `--part 92020S` a mode-0xE FLUSHPBE is refused.  Be's
      kernels do not use one.
- **What the manuals do not give**: they say nothing about an address
  rule for FLUSHPBE on any part, and nothing about a 92020 ID.  The
  92010's field layout (p. 1-11) is all they offer.  The 92020's value,
  `0x0E33D03B`, is pinned only by Be's kernels.

### No 92020-only instructions

- **Sweep**: a linear sweep of each kernel's whole `.text`, aware of the
  CPU prefix.  Nov is 0x1ec80 bytes, 35,378 instructions; Mar is
  32,190.  The installer's `.text` is Nov's.
- **What it found**: no instruction outside the 92010's tables.  The
  niladics used are CPU, KRET, NOP, FLUSHI, FLUSHP, CRET and TESTC.
  There are no trapped niladics, no `unimp*` dyadics, and no reserved
  opcode or subcode.  FLUSHPBE appears 3 times, FLUSHPTE once, DQM 10
  times.
- **Lines that are not new opcodes**: the sweep's "unimplemented" lines
  are mode 0x7 (`Roffset:UH`) operands without a CPU prefix.  That is a
  legal 92010 mode (PRM Table 1-21, p. 1-25) which the disassembler
  prints only after CPU.
- **The idle loop**: `_null_thread` spins on a call.  `_wait_for_interrupt`
  is an ordinary C function.  WFI is not used.
- **Caveat**: a linear sweep can mis-split code that has data
  interleaved.  Every text symbol (913 in Nov, 882 in Mar) fell on an
  instruction boundary of the sweep, so that risk is small.

### The disassembler and mode 0x7

MetaWare emits operand mode 0x7 without a CPU prefix: `Roffset:UH`, the
unsigned half-word stack offset of Table 1-21 (PRM p. 1-25).  The BeBox
agent counted 43 sites.  `asm/hobbit_asm.py`'s disassembler used to
print these as "unimplemented … (CPU prefix required for mode 7)",
although the assembler accepts `R42:UH` and `sem/hobbit_sem.py` executes
it.

- **The fix**: the disassembler now prints them, for example `OR
  $4,R42:UH` (Be's `_sysinit2`).  After CPU, mode 0x7 is still the
  register mode (Table 1-22, p. 1-26).
- **The test**: `tests/test_hobbit_asm.py`
  `test_mode_7_without_cpu_is_unsigned_half_stack_offset` round-trips
  four of Be's encodings through the disassembler and the assembler.

### `-mask5` and `-nodqm`

The `.comment` sections record the compiler lines:

- `hc2.5e/2.5g/2.6g -O3 -mask5` for Be's own sources;
- `-O4 -mask5 -nodqm` for 31 MetaWare library files (`/sol/lib/libc_l/…`:
  stdio, `_doprint`, the `xadd`/`xmul` soft-float helpers, etc.).

**Neither option is defined in any manual found.**

- The PRM and the data sheet know masks one and two only (version
  codes 0 and 1, PRM p. 1-11).  The 92020 ID's version code is 0.
- **`-mask5` cannot be tied to a mask from these sources.**  It could
  be a MetaWare code-generation level, or a mask revision of the 92010
  or 92020; that is unresolved.
- **`-nodqm` most plausibly means "do not generate DQM"** (PRM p. 3-18,
  double- or quad-word move).  That is a reading of the name only.
- The kernel's own objects were built without `-nodqm`, yet every DQM
  in the kernels sits in hand-written or library code:
  - `cs_1` and `check_stack` beside the assembly entry stubs;
  - MetaWare's `memcpy`, `__rmemcpy`, `strcat` and `strlen`;
  - the `__mwdiv422`/`__mwmul224` helpers.

  No DQM was found in a function compiled from one of Be's `.c` files.
  So whether the compiler emits DQM without `-nodqm` cannot be shown
  from these binaries, and why the library was built with it is not
  stated.
- MetaWare's High C manual for Hobbit is in "Not found".

## The model's part switch

`sem/hobbit_sem.py`:

- **Parts**: `Part`, `PARTS`, `REFUSED_PARTS` and `part_info()`.
  `State.part` defaults to `"92010"`, and `State.borrow_92010_timing`
  defaults to False.
- **CLI**: `--part 92010|92020S` and `--borrow-92010-timing`.
- **Fast path**: a 92010 run takes it, and its behaviour, records and
  refusals are unchanged.
- **The 92020S**:
  1. **ID register** reads `0x0E33D03B` (with a `System`).
  2. **Refusals** (`Unsourced92020`, a subclass of `Unsupported`, so
     every existing caller still stops on it):
     - unassigned encodings, where WFI may live;
     - a FLUSHPBE whose address and target differ in bit 10, and one
       whose operand is stack offset indirect (mode 0xE, target
       ambiguous);
     - a CONFIG write that sets bits 15:0;
     - every step, unless the run has opted in to the borrowed timing.
- **92020M and 92020MX**: refused with a reason.  So is any other name,
  including a bare `92020`; that refusal is deliberate, because "92020"
  alone does not say which bus.
- **No timing twin**: `sem/hobbit_timing.py` does not exist on master
  (checked 2026-11-24 after `git fetch`; `sem/` holds only
  `hobbit_sem.py`).
- **Not changed**: `bsv/` and `fpga/` belong to other agents.

Tests: `tests/test_sem_part.py`.  Its header lists each injected bug and
the failures observed.

## What would settle the open points

- An AT&T 92020 data sheet or PRM supplement would give:
  - WFI's encoding, timing, and the PC an interrupt saves;
  - the CONFIG bits;
  - the FLUSHPBE address rule;
  - any timing differences.
- Be's kernel source, or a third kernel, would show which FLUSHPBE
  pairing was right.  A Be build that executes WFI would give its
  encoding by usage; under AGENTS.md that is enough to look for, but
  not to implement from alone.
- MetaWare's Hobbit High C documentation would define `-mask5` and
  `-nodqm`.
