# Golden 025 — a store whose translation faults: exception 9 at the store, nothing retired after it

The first golden run on the **privileged harness** (`README.md`, "The
privileged harness"): virtual addressing, a segment and a page table, and
a fault vector, so an exception is followed by its handler's records.

Two findings of the s9term boot on the core (`docs/conformance_1to1.md`
§1d, rows 9 and 10) are pinned here:

1. **A store whose translation faults is precise.**  At record 2,893,033
   of the boot the kernel's `evenaddr` stores to the user address
   `0xffbfffec`, which has no writable mapping.  The reference takes
   exception 9 at the store, which does not retire: a `trap=1` record with
   no write.  The core had already retired the store (its record carried
   the write) when the data face reported the fault a clock later, and
   then took the exception.  The printed basis: the exception sequence
   saves "PC of faulted instruction" (p. 1-38, read from the page image);
   a write fault is signalled "during an address translation for ...
   writing data" (p. 2-3); and p. 1-39 makes an exception of exactly one
   case -- "For a data write *bus error*, the PC placed on the interrupt
   stack is not the PC of the instruction associated with the faulted
   access" because of "the *unhinged* nature of the stores" -- which is
   exception 0xA, not the MMU's 0x9.  That the translation is checked
   before the store unhinges, and only the bus access is late, is the
   reading this golden encodes; pp. 1-16 ("To remain restartable ...") and
   3-6 (the interlocked forms are "not restartable from this point")
   assume faulting instructions restart.
2. **Nothing younger retires while the exception sequence runs.**  At
   record 3,298,054 of the boot (its second interrupt) EU_S1 held an
   instruction when the sequence started; `stop` leaves a full slot full,
   and the decoded store had just been emptied, so an all-zero entry went
   on through EU_S2 and EU_S3 and retired as a record of PC 0 before the
   handler.  Here the faulting store is on a loop's second pass, so the
   instructions behind it are already decoded and EU_S1 is full when the
   exception starts.

## How this file was derived

By hand from the printed tables, before either model ran this image.  The
parcels were written from the encoding tables and disassembled with
`asm/hobbit_asm.py --disasm` as a cross-check (it agreed).  `sem/` then
reproduced every line as derived; neither `sem/` nor `bsv/` produced or
corrected any field.  (An earlier, shorter draft without the loop passed
the core with finding 2's fix removed -- EU_S1 was still empty on a cold
decoded store when the exception started -- so the loop was added.)

## Pre-state

The fixed pre-state of `README.md` -- PC 0, SP `0x100`, MSP `0x180`,
SHAD = SP, memory zero except the image -- with:

* PSW `0x00010200`: V (bit 16, virtual addressing, Table 1-8 p. 1-14),
  CSP = SP (bit 9), kernel level.
* STB `0x1000`; segment 0's entry at `0x1000` is `0x00002001` (paged,
  page table at `0x2000`, valid: Table 2-1, p. 2-5); the page table has
  `0x00000003` at `0x2000` (page 0 to frame 0, writable, valid) and
  `0x00003001` at `0x200c` (page 3 to frame 3, valid, **not writable**:
  Table 2-3, p. 2-7).  Every other page is invalid.  Kernel level, so the
  user bit is not checked; the writable bit is (p. 2-3).
* VB `0x40`, and the word at `0x44` (`VB+4`, the exception vector,
  p. 1-38) is `0x00000020`.  ISP `0x200` (`README.md`), so the frame the
  sequence writes (`ISP-12` .. `ISP-4`) is in page 0, away from the image.

`sem/hobbit_sem.py --system --stb 0x1000 --poke ADDR=WORD ...` puts the
table entries and the vector word in physical memory; `bsv/run_golden.sh
025` writes the same table entries to the MMU core's table memory, STB and
VB through the core, and the vector word to the event unit's memory.

## Discriminating check (observed 2026-11-24)

Each injected into `bsv/HobbitCore.bsv` alone, the golden rebuilt and run,
and the file restored byte for byte from a saved copy:

| injection | observed |
|---|---|
| `storeFaults` always False (the store commits; the fault comes from the data face a clock later, as before) | fails at L07, `we` 1 for 0 (the record carries the write to `0x3000`) |
| `deliver` and `move2to3` not held while the event sequence runs (`!eventActiveR` removed) | fails at L08: an extra record with every field 0 (`pc=0000 insn=00000000`) before the handler -- the boot's record 3,298,054 |
| the box's `toMemory` test dropped (every store checked, cache-resident ones too) | **every line still matches**: no store here goes into the cache window of a non-writable page, so this golden does not pin that half |

The first draft (the store on its first pass, no loop) failed the first
injection and passed the second; that is why the loop is there.
