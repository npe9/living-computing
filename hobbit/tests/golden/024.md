# Golden 024 — `CATCH` with a target from memory: absolute and stack-offset-indirect

`CATCH` takes a Table 3-2 `word32` source (p. 3-11), and its description
(p. 3-10, read from the page image) gives the target MSP per mode:

* "If the source operand is defined with a stack offset indirect mode
  (*Roffset), the target value for the MSP is fetched from memory (or the
  stack cache) at the address formed by adding the offset to SP
  (MSP = *(offset + SP))."
* "If the source operand is defined with an absolute mode ($addr), the
  target value for the MSP is fetched from memory (or the stack cache) at
  the address specified in the absolute address (MSP = *(addr))."

The core decoded only the stack-offset (`0xD`) and immediate (`0xF`)
three-parcel forms and took the bad-mode trap for the rest.  It was found
on the s9term boot (docs/p9boot.md, "The boot on the core"): the kernel's
interrupt return executes `CATCH *R4` (`80e8 0000 0004`) at `0x80004334`,
record 2,849,530, where the reference retired it and the core took the
unimplemented-instruction trap (docs/conformance_1to1.md §1d, finding 4).

No earlier golden executes `CATCH` at all.

## Program

Three-parcel dyadic: `10 | opcode << 8 | smode << 4 | dmode` (Table 1-18,
p. 1-24), `MOV` = `0x06`.  Three-parcel monadic: opcode `0x00`, the mode in
the smode nibble, the subcode in the low nibble, one 32-bit operand in
parcels 2 and 3 (Table 1-19 p. 1-24, p. 1-23); `CATCH` is subcode `0x8`
(p. 3-11, "6 0x00 0x8 CATCH word32").  Modes (Table 1-21, p. 1-25): `0xC`
absolute, `0xD` stack offset, `0xE` stack offset indirect, `0xF`
immediate.  The forms are golden 019's `ENTER *$0x0224` (`80c9`) and
`ENTER *R8` (`80e9`) with subcode 8 for 9.

## Pre-state

The fixed pre-state of `README.md`: PC `0x00000000`, PSW `0x00000200`,
SP `0x00000100`, MSP `0x00000180`, memory zero except the image.  CSP is
SP (PSW bit 9 = 1), so `CATCH` is not a no-op (p. 3-10).  SCSIZE is 64
words (p. 1-6), so no fill takes MSP past `SP + 0x100 = 0x200`.

## Retirement lines

L01. `HRI pc=0000 insn=86fc01a0 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=00000240 data=000001a0 mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (p. 3-32): the memory word `0x240` (outside the window
`[0x100, 0x180)`) receives `0x1a0`, the first target.

L02. `HRI pc=0006 insn=80c80000 sp=00000100>00000100 msp=00000180>000001a0 we=0 addr=00000000 data=00000000 mask=00 trap=0 cyc=1`

Cycles: 1 — Table 4-36 (p. 4-5) prints `CATCH` as a flat 1.

Transition (pp. 3-10, 3-11): `CATCH *$0x0240`, absolute: the target is
the *word at* `0x240`, `0x1a0` (not `0x240`, which would fill to the
`0x200` limit).  `MSP < 0x1a0`, so the cache is filled in 16-byte blocks
from `0x180`: two blocks, MSP `0x180 -> 0x1a0`.  No write.

L03. `HRI pc=000c insn=86fd01c4 sp=00000100>00000100 msp=000001a0>000001a0 we=1 addr=00000108 data=000001c4 mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (p. 3-32): the stack word `SP+8 = 0x108` receives `0x1c4`.

L04. `HRI pc=0012 insn=80e80000 sp=00000100>00000100 msp=000001a0>000001d0 we=0 addr=00000000 data=00000000 mask=00 trap=0 cyc=1`

Cycles: 1 — `CATCH` (Table 4-36, p. 4-5).

Transition (pp. 3-10, 3-11): `CATCH *R8`, stack offset indirect: the
target is the word at `SP + 8 = 0x108`, `0x1c4` (not `0x108`, which is
below MSP and would leave it where it is).  `0x1c4` is not a multiple of
16, so "the cache is filled to the next multiple of 16" (p. 3-11): three
blocks from `0x1a0`, MSP `0x1a0 -> 0x1d0`.

L05. `HRI pc=0018 insn=2c020000 sp=00000100>00000100 msp=000001d0>000001d0 we=0 addr=00000000 data=00000000 mask=00 trap=0 cyc=1`

Cycles: 1 — `NOP` (Table 4-36, p. 4-5).  Transition (p. 3-35): no write.

L06. `HRI pc=001a insn=2c020000 sp=00000100>00000100 msp=000001d0>000001d0 we=0 addr=00000000 data=00000000 mask=00 trap=0 cyc=1`

Cycles: 1 — `NOP` (Table 4-36, p. 4-5).  Transition (p. 3-35): no write.

## Discriminating check (observed 2026-11-24)

Each bug was injected into `bsv/` and `bsv/run_golden.sh 024` was re-run.
The output was compared with this trace using `hri_check.py`, which stops
at the first line that differs. The file was then written back byte for
byte, using `build/coreboot/inject_golden.py` (not committed). The core and
the reference model both reproduce the six lines as derived, `cyc`
included.

| injected bug | first failing line | what the core did |
|---|---|---|
| the decoder refuses modes `0xC`/`0xE` (the state before) | L02 | the bad-mode trap; MSP stays `0x180` |
| CATCH's memory forms reach EU_S2 unconverted (EU_S1 reads no word) | L02 | MSP `0x180 -> 0x200`: the field `0x240` used as the target, clamped at `SP + 0x100` |
| the operand field taken as the target for both modes | L02 | the same as the row above |
| mode `0xE` takes the word the pointer points to, not the pointer word | L04 | MSP stays `0x1a0`: the word at `0x1c4` is 0 |
