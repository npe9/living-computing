# 006 — FLUSHD, an unimplemented opcode, taking the unimplemented-instruction trap

This trace fixes the unimplemented-instruction sequence (p. 1-39) using
FLUSHD, a Table 3-1 mnemonic that is not implemented in hardware because the
part has no data cache (p. 3-22). The affected niladic subcode is `0x006` of
niladic opcode `0x0B` (Table 1-17 p. 1-22). Nothing here was produced or
checked by `bsv/`, `asm/` or `sem/`.

The sequence is *not* the exception sequence of p. 1-38: it performs no
interrupt-stack frame, saves no PSW and takes no exception ID. It stores the
PC of the unimplemented opcode in the word at CSP (p. 1-39) and then fetches
from `*(VB+12)`. The PC is parcel-aligned — bits 31:1 with bit 0 reserved
(Table 1-7, p. 1-14) — so the word stored is the address of the FLUSHD parcel
itself, 0x00000006.

The image is 2 word(s) = 8 byte(s); the program is 4 instruction(s), of which 4 retire in this run.

word at that address and the parcel at the following address bits 15:0

## Pre-state

Every run in this directory starts from the single pre-state fixed in
`README.md`:

| register | value | why |
|---|---|---|
| PC | `0x00000000` | reset start address, p. 1-36 |
| PSW | `0x00000200` | bit 9 = 1 makes SP the CSP (Table 1-8 sheet 2, p. 1-15); every other bit 0: kernel level, physical addressing, interrupts inhibited (IPL 0), tracing off |
| CONFIG | `0x00000000` | reset value: all caches disabled, demand prefetch, PC extension 0 (p. 1-36, p. 1-10) |
| SP | `0x00000100` | quad-aligned (p. 1-17) |
| MSP | `0x00000180` | quad-aligned, `SP <= MSP <= SP+256` (p. 1-13) |
| SHAD | `0x00000100` | p. 1-15: a direct write of PSW bit 9 requires SHAD to be updated to the new SP |
| ISP | `0x00000200` | quad-aligned (p. 1-12); never used, because PSW bit 9 selects SP |
| VB | `0x00000000` | never read inside a trace; the trap's `*(VB+12)` fetch is outside the trace |
| memory | image at address 0, `0x00000000` elsewhere | `README.md`, "Memory" |

SP and MSP are quad-aligned stack pointers whose low 4 bits do not exist
(p. 1-17, p. 1-13), so no operand in these programs can be misaligned.

## Retirement lines

One line per retired instruction, in program order, in the fixed HRI format.
`Lnn` numbers are used only by this document; the `.trace` file holds the same
lines without them.

L01. `HRI pc=0000 insn=2c020000 sp=00000100>00000100 msp=00000180>00000180 we=0 addr=00000000 data=00000000 mask=00 trap=0`

Encoding: Niladic `0x0B`/`0x002` (Table 1-17 p. 1-22; p. 3-35). Parcel 0x2c02.

Transition: No operation, no write; execution starts at PC = 0x0000 (p. 1-36).

L02. `HRI pc=0002 insn=71400000 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=00000100 data=0000000a mask=0f trap=0`

Encoding: One-parcel `MOV.CS`, opcode `0x1C`, `imm5`=10 in bits 9:5 (sign-extended, p. 1-21), `stk5`=0 in bits 4:0 (Table 1-15 p. 1-22; p. 3-32). Parcel 0x7140.

Transition: *(CSP+0) = *(0x00000100) becomes 0x0000000a. The value is deliberately not 6 and not 8: the trap at 0x0006 stores 0x00000006 in this same word, so a model that skipped the trap's store, or stored the preceding instruction's PC, cannot be rescued by an accidental match, and the trace distinguishes 0x0000000a from 0x00000006 on this address.

L03. `HRI pc=0004 insn=2c020000 sp=00000100>00000100 msp=00000180>00000180 we=0 addr=00000000 data=00000000 mask=00 trap=0`

Encoding: Niladic `0x0B`/`0x002` (Table 1-17 p. 1-22; p. 3-35). Parcel 0x2c02.

Transition: No operation. It separates the pre-load from the trap so that the two stores to 0x00000100 are not adjacent.

L04. `HRI pc=0006 insn=2c060000 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=00000100 data=00000006 mask=0f trap=1`

Encoding: Niladic opcode `0x0B` in bits 14:10 and subcode `0x006` in bits 9:0 (Table 1-17 p. 1-22 — the row is OCR'd `FLUSHC`, the page image and p. 3-22 name FLUSHD). Parcel 0x2c06.

Transition: p. 3-22: there is no data cache, so "an unimplemented instruction sequence is taken", which is `*(CSP) = PC of unimplemented opcode` and `PC = *(VB+12)` (p. 1-39). CSP = SP = 0x00000100 and the saved PC is the address of the FLUSHD parcel, 0x00000006 (PC is parcel-aligned, Table 1-7 p. 1-14), so the line's one write is 0x00000006 at 0x00000100 and `trap=1` marks the instruction. The vector fetch that follows is outside the trace (`README.md`, stop rule 1).

## Manual ambiguities and the choices they forced

- Table 1-17's FLUSHD row is OCR'd as `FLUSHC`; p. 3-22 prints the name FLUSHD and states the unimplemented sequence, and the subcode is `0x6` either way, so the parcel 0x2c06 does not depend on which reading is taken.

- The fixed HRI line carries one write. The unimplemented-instruction sequence performs one architectural store, `*(CSP) = PC of the unimplemented opcode` (p. 1-39), so this directory reports it with `we=1`, `addr` = CSP and `data` = that PC. A model that reported no write for a trap would differ on this single line; the choice is stated here so the difference is a test result rather than a silent disagreement.

- The PC saved is the address of the unimplemented opcode itself, 0x00000006: p. 1-39 saves the *PC of the opcode*, and a PC is the address of the current instruction with bit 0 reserved (Table 1-7 p. 1-14, p. 1-13). The following parcel would be 0x00000008 and the preceding instruction's address 0x00000004; neither is the documented value, and L02's 0x0000000a rules out the coincidence that would hide a missing store.

- p. 1-39 converts three cases to illegal instructions (exception 0x3): an unimplemented *monadic* with a non-word mode, an unimplemented instruction after `CPU` with an illegal mode, and a negative `RETURN`. FLUSHD is a niladic with no operands and is none of them, so `trap=1` rather than exception 0x3 is the documented outcome.

- The manual does not say where execution goes after `PC = *(VB+12)`; VB = 0 here would point the fetch into this program's own text. The trace makes no claim after the trap line, which is why no instruction follows FLUSHD in the image and why `README.md` stop rule 1 ends the run there.

- The pre-load is `MOV $10, R0` rather than a value equal to the saved PC. The instruction is unconstrained by the manual; the choice is what keeps the trap's store observable, as L02 explains.
