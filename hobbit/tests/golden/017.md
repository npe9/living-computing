# Golden 017 — little-endian data: PSW.UL selects the byte lanes

This trace fixes the *numbering of bytes within data words* when the
user little-endian bit is set (printed pp. 1-3, 1-4):

> "The numbering of bytes, within data words, is selectable for the User
> and Kernel modes. The User mode is set via the program status word
> (PSW) UL-bit (User Little endian-bit). The Kernel mode is set via the
> configuration register (CONFIG) KL-bit (Kernel Little endian-bit)."
> — p. 1-3
>
> Figure 1-3, Little-endian Byte Ordering: `| 31 BYTE3 24 | 23 BYTE2 16 |
> 15 BYTE1 8 | 7 BYTE0 0 |` — p. 1-4

So with PSW bit 15 set at user level (PSW bit 10 set), the byte at a
word address is bits 7:0, the byte at address+1 is bits 15:8, and the
half-word at an even offset is bits 15:0 or, at offset 2, bits 31:16.
"Text is always in big-endian order" (p. 1-4 note): the parcels of this
image are laid out exactly as in every other golden.

1st Edition Plan 9 runs every process this way
(`sys/src/9/hobbit/machine.h:77`, `PSW_UL`), which is why this golden
exists: until 2026-11-20 both models were big-endian only.

The image is 18 words = 72 bytes; the program is 12 instructions and all
12 retire.

## How this file was derived

By hand, from the printed pages, before either model ran with the bit
set: the parcels from Tables 1-18/1-20/1-21, the values from Figure 1-3.
Neither `asm/` nor `sem/` nor `bsv/` produced or corrected any field.

## Pre-state — not the README's

PC `0x00000000`, **PSW `0x00008600`** — bit 15 (UL, user little-endian),
bit 10 (execution level: user) and bit 9 (CSP = SP), Table 1-8
pp. 1-14..1-16 — SP `0x00000100`, MSP `0x00000180`, SHAD `0x00000100`,
ISP `0x00000200`, VB `0`, CONFIG `0`, memory zero except the image.
The harnesses start this golden with that PSW: `sem/hobbit_sem.py --psw
0x8600` and `bsv/run_golden.sh`'s `startPsw` for stem 017.  CONFIG.KL
is 0, so the same program at kernel level would be big-endian; the
kernel half of the rule is pinned by `tests/test_p9run.py`
(`test_user_bit_is_ignored_at_kernel_level_and_kl_decides`), not here.

## Program

Every instruction is a `MOV` (opcode `0x06`, p. 3-32): the first is the
five-parcel form (`11 | opcode << 8 | smode << 4 | dmode`, Table 1-20
p. 1-25), the rest are three-parcel (`10 | ...`, Table 1-18 p. 1-24),
and the last parcel is `NOP`.  Modes are Table 1-21's (p. 1-25): `0`
`*$addr:B`, `1` `*$addr:UB`, `3` `*$addr:UH`, `4` `Roffset:B`, `5`
`Roffset:UB`, `6` `Roffset:H`, `7` `Roffset:UH`, `D` `Roffset:W`, `F`
`$data`.  The 16-bit fields are unscaled byte offsets or addresses
(p. 1-21 scales only the five- and ten-bit fields); a 16-bit immediate
is sign-extended and a 16-bit absolute address is zero-extended with
CONFIG's PC-extension bit clear (p. 1-23).

## Retirement lines

Cycle accounting: `MOV` is 1 in Table 4-32 (p. 4-3) and `NOP` is 1
(Table 4-36, p. 4-5); the p. 4-1 assumptions charge no operand-access
delay, so the two operands in memory (L09..L11) add nothing to `cyc`,
as in golden 016.  No SP/MSP changes occur.  The `mask` convention is by
lane (bit 3 = bits 31:24, bit 0 = bits 7:0), so the lane a byte lands in
is visible in the record.

L01. `HRI pc=0000 insn=c6fd1122 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=00000108 data=11223344 mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (Figure 1-3, p. 1-4): `SP+8 = 0x108` receives the word `0x11223344`.  Little-endian, its bytes
are `0x44` at `0x108`, `0x33` at `0x109`, `0x22` at `0x10a`, `0x11` at
`0x10b` (Figure 1-3).

L02. `HRI pc=000a insn=865d0008 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=0000010c data=00000044 mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (Figure 1-3, p. 1-4): The unsigned byte at `0x108` is BYTE0, bits 7:0: `0x44`.  (Big-endian it
would be `0x11`.)  `SP+12 = 0x10c` receives `0x00000044`.

L03. `HRI pc=0010 insn=865d0009 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=0000010c data=00000033 mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (Figure 1-3, p. 1-4): The byte at `0x109` is BYTE1, bits 15:8: `0x33`.  (Big-endian: `0x22`.)

L04. `HRI pc=0016 insn=867d000a sp=00000100>00000100 msp=00000180>00000180 we=1 addr=0000010c data=00001122 mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (Figure 1-3, p. 1-4): The half-word at `0x10a` is BYTE2 and BYTE3, bits 31:16: `0x1122`.
(Big-endian: `0x3344`.)

L05. `HRI pc=001c insn=86f400ab sp=00000100>00000100 msp=00000180>00000180 we=1 addr=00000108 data=0000ab00 mask=02 trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (Figure 1-3, p. 1-4; p. 1-4 "Alignment": stores are done to word addresses with the write strobes enabled): A byte store to `0x109`: BYTE1, lane 1, so the byte mark is `0x02` and
the bus word carries `0xab` in bits 15:8.  The record's `addr` is the
containing word, `0x108`, which becomes `0x1122ab44`.  (Big-endian the
mark would be `0x04` and the data `0x00ab0000`.)

L06. `HRI pc=0022 insn=86f6beef sp=00000100>00000100 msp=00000180>00000180 we=1 addr=00000108 data=0000beef mask=03 trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (Figure 1-3, p. 1-4; p. 1-23): The immediate is `0xffffbeef` (sign-extended); the half-word store to
`0x108` takes its low 16 bits into BYTE0 and BYTE1, bits 15:0: marks
`0x03`, data `0x0000beef`.  The word becomes `0x1122beef`, and the byte
L05 wrote is overwritten.  (Big-endian: marks `0x0c`, data
`0xbeef0000`.)

L07. `HRI pc=0028 insn=864d0008 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=0000010c data=ffffffef mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (Figure 1-3, p. 1-4): The signed byte at `0x108` is `0xef`, sign-extended to `0xffffffef`
(p. 1-28).  (Big-endian: `0x11`.)

L08. `HRI pc=002e insn=866d0008 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=0000010c data=ffffbeef mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (Figure 1-3, p. 1-4; p. 1-28): The signed half-word at `0x108` is `0xbeef`, sign-extended.
(A big-endian read of this word would give `0x1122`.)

L09. `HRI pc=0034 insn=86f0005a sp=00000100>00000100 msp=00000180>00000180 we=1 addr=00000200 data=00005a00 mask=02 trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (Figure 1-3, p. 1-4): A byte store to the absolute address `0x201`, which is outside the stack
cache's window `[0x100, 0x180)` and so is a word of memory (p. 1-5):
lane 1, marks `0x02`, data `0x00005a00`; the word at `0x200` was zero
and becomes `0x00005a00`.

L10. `HRI pc=003a insn=861d0201 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=0000010c data=0000005a mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (Figure 1-3, p. 1-4): The unsigned byte read back from memory at `0x201`: bits 15:8 of
`0x00005a00`, `0x5a`.  (Big-endian lanes on both L09 and L10 would also
read back `0x5a` — this line alone does not discriminate; L09's mask and
L11 do.)

L11. `HRI pc=0040 insn=863d0200 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=0000010c data=00005a00 mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition (Figure 1-3, p. 1-4): The unsigned half-word at `0x200` is bits 15:0 of `0x00005a00`:
`0x5a00`.  (With big-endian lanes throughout, L09 would have put the
byte in bits 23:16 and this half-word, bits 31:16, would read `0x005a`.)

L12. `HRI pc=0046 insn=2c020000 sp=00000100>00000100 msp=00000180>00000180 we=0 addr=00000000 data=00000000 mask=00 trap=0 cyc=1`

Cycles: 1 — `NOP` min=max=1 (Table 4-36, p. 4-5).

Transition (p. 3-35): `NOP`: no write.

## Discriminating check (observed 2026-11-20)

Each bug was injected into `bsv/HobbitTypes.bsv`, `bsv/run_golden.sh
017` re-run, and the file restored; the clean run after the last one
matched all 12 lines.

| injected bug | lines that failed | what the core printed |
|---|---|---|
| the core ignores PSW.UL (`dataLittle` = False) | L02 L03 L04 L05 L06 L07 L09 L11 | L02 `data=00000011`, L03 `00000022`, L04 `00003344`, L05 `data=00ab0000 mask=04`, L06 `data=beef0000 mask=0c`, L07 `ffffffbe`, L09 `data=005a0000 mask=04`, L11 `0000005a` |
| half-word lane not swapped (`halfHigh` big-endian) | L04 L06 L07 L11 | L04 `00003344`, L06 `data=beef0000 mask=0c`, L07 `00000044`, L11 `00000000` |
| byte lane not swapped (`byteLane` big-endian) | L02 L03 L05 L07 L09 L11 | L02 `00000011`, L03 `00000022`, L05 `data=00ab0000 mask=04`, L07 `00000011`, L09 `data=005a0000 mask=04`, L11 `00000000` |
| execution-level test inverted (user level takes CONFIG.KL) | L02 L03 L04 L05 L06 L07 L09 L11 | as the first row |

L08 and L10 never failed: each reads back, through the same lanes, what
an earlier line stored (L06's half-word, L09's byte), so a consistent
wrong order cancels — the parenthesised "big-endian" values in L08 and
L10 above describe a big-endian *read of a little-endian store*, not
these injections.  That cancellation is exactly why `cat` passed A1 with
the wrong byte order.

On the reference model, running this image with the README's PSW
(`0x200`, big-endian) fails at L02 (`dut=0x00000011 spec=0x00000044`).

Not covered here, on the core: CONFIG.KL at kernel level (`setConfigKl`).
The reference model's half of that rule is in `tests/test_p9run.py`; the
core's has no test yet.
