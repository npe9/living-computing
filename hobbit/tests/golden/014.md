# Golden 014 — stack-offset-indirect word operands: `MOV.IS`, `MOV.II`, `MOV.SI`

This trace fixes Table 1-21's word stack-offset-indirect mode `0xE`
(printed p. 1-25) and its one-parcel `istk5` spellings, `MOV.IS`
(opcode `0x19`), `MOV.SI` (`0x1A`) and `MOV.II` (`0x1B`) in Table 1-15
row 11 (printed p. 1-22). p. 1-27 defines the mode: "Stack Offset
Indirect - addressing adds a constant offset in the instruction to the
address of the current stack pointer (CSP). The word at this address is
fetched and then used as an address to obtain the data operand. The
offset must be word aligned. An alignment fault (0x4) is executed if the
offset is not word aligned." The write's address in every line below is
therefore the *pointer's value*, never the stack slot that holds the
pointer, and the two operands are independent: a source pointer and a
destination pointer are both resolved.

The image is 24 words = 96 bytes; the program is 16 instructions and all
16 retire.

## Program

A three-parcel first parcel is `10 | opcode[5:0] << 8 | smode << 4 |
dmode`; a five-parcel first parcel is the same with `11` (pp. 1-24,
1-25). `MOV` is opcode `0x06`, `$data` is mode `0xF`, `Roffset:W` is
`0xD` and `*Roffset:W` is `0xE` (Table 1-21, p. 1-25). A 16-bit field is
sign-extended in immediate and offset modes and a 32-bit field is used
as it stands (p. 1-23). A one-parcel field is `opcode[4:0]` in bits
14:10, the 5-bit source in bits 9:5 and the destination in bits 4:0;
`stk5`/`istk5` are zero-extended and multiplied by four (pp. 1-21,
1-22).

## Pre-state

The fixed pre-state of `README.md`: PC `0x00000000`, PSW `0x00000200`
(bit 9: CSP = SP, p. 1-14), SP `0x00000100`, MSP `0x00000180`,
SHAD `0x00000100`, ISP `0x00000200`, VB `0`, CONFIG `0`, memory zero
except the image. The stack-cache window is `[0x100, 0x180)`; every
pointer target below (`0x114`, `0x118`, `0x120`) is inside it, and every
one of them is written by an earlier line before it is read.

## Retirement lines

One line per retired instruction, in program order, in the fixed HRI
format. Cycle accounting: `MOV` is 1 in Table 4-32 (p. 4-3) for every
form, including the indirect ones: the p. 4-1 assumptions do not admit
indirect operands, so no Table 4-37..4-40 operand-access delay is added,
and the duplicated indirect rows of Tables 4-38 and 4-40 are not
double-counted (`sem/README.md`, choice 22). No SP/MSP changes occur.

L01. `HRI pc=0000 insn=86fd0114 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=00000104 data=00000114 mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Encoding: `86fd` = `10` prefix, opcode `0x06` (`MOV`), smode `0xF` (`$data`), dmode `0xD` (`Roffset:W`); source parcel `0x0114`, destination parcel `0x0004` (Tables 1-18/1-21, pp. 1-24, 1-25).

Transition: `dst = src` (p. 3-32). `0x0004` is an unscaled byte stack offset (p. 1-21 scales only five- and ten-bit fields), so the destination is `SP+4 = 0x104`, which receives `0x00000114`. This is the pointer slot the indirect forms later read.

L02. `HRI pc=0006 insn=86fd0118 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=00000108 data=00000118 mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Encoding: same first parcel `86fd`; source `0x0118`, destination `0x0008` (Tables 1-18/1-21).

Transition: writes `0x00000118` at `SP+8 = 0x108`, the second pointer slot.

L03. `HRI pc=000c insn=86fd011c sp=00000100>00000100 msp=00000180>00000180 we=1 addr=0000010c data=0000011c mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Transition: writes `0x0000011c` at `SP+12 = 0x10c`, the third pointer slot.

L04. `HRI pc=0012 insn=c6fe1111 sp=00000100>00000100 msp=00000180>00000180 we=1 addr=00000114 data=11112222 mask=0f trap=0 cyc=1`

Cycles: 1 — `MOV` min=max=1 (Table 4-32, p. 4-3).

Encoding: `c6fe` = `11` prefix (five parcels), opcode `0x06`, smode `0xF`, dmode `0xE` (`*Roffset:W`); 32-bit source `0x11112222`, 32-bit destination `0x00000004` (Table 1-20 p. 1-25; Table 1-21 p. 1-25).

Transition: the pointer at `0x108` is `0x118` (L02), so `0x33334444` is written at `0x118`.

## Manual ambiguities and the choices they forced

- The offset's unit is a byte, not a word index: p. 1-21 scales only the five-bit and ten-bit fields, and p. 1-27 adds "a constant offset in the instruction to the address of the current stack pointer". L04's destination offset `0x0004` must name `0x104`; a word-index reading would name `0x110` and no pointer would be found.

- The one-parcel `istk5` is a different unit from the three-parcel offset: it is a five-bit word index multiplied by four (pp. 1-21, 1-22), so `istk5` 1 names `0x104` while a three-parcel field `0x0001` would name `0x101` and be an alignment fault. L07-L09 pin the scaled reading.

- p. 1-27 requires the *offset* to be word-aligned; it says nothing about the pointed-to address, whose own width rule is p. 1-4's. L12-L15 therefore use an aligned offset (`0x0c`) to produce an unaligned byte address (`0x121`) and an aligned half-word address (`0x122`). A model that checked the target against word alignment would refuse L13 and L15; one that checked only the target would accept a misaligned offset.

- The 32-bit immediate at L11 is written as a five-parcel `$data` so the byte and half-word lanes are exact. A three-parcel `$data` sign-extends its 16-bit field (p. 1-23), which would put `0xffff` in the upper half and change the byte at `0x121`; that would test sign extension rather than the indirect addressing rule this golden is about.

- L08 overwrites L05's destination word and L09 overwrites L08's: the two lines would still produce the same *addresses* if the roles were swapped, but not the same values. Keeping both values different (`0x11112222` vs `0x55667788`) is what makes the two operand roles observable.
