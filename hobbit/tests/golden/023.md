# Golden 023 — a wrong-path operand read that would fault must not raise the exception

The s9term boot on the core (docs/p9boot.md, "The boot on the core")
diverged at record 2,658,001 (2,681,671 on the reference boot as merged
2026-11-23, which also reads the EEPROM and the rtc), in the kernel's
`netadd`:

```text
CMPEQ $0, R24        ; is the pointer nil?
JMPTN ...            ; yes: jump (predicted not taken, folded)
CMPEQ *R24, R0       ; the not-taken path dereferences the pointer
```

On the pass where the pointer was nil the branch was taken, but the core
had already fetched the not-taken path's operand `*R24` -- virtual address
0, which the kernel leaves unmapped -- and the MMU's fault started the
exception sequence at once, although the instruction that read it was
never going to retire.  The printed architecture takes an exception at
the faulting instruction, which has not completed (p. 1-37, p. 1-38); an
instruction that never executes cannot fault.

This golden is that sequence, reduced.  It is a two-pass loop with the
`netadd` shape: a folded `JMPTN` predicted not taken, followed on the
not-taken path by `MOV *R24, R8`.  On the first pass the branch falls
through and the `MOV` executes, reading a word inside the stack cache.
Then R24 is pointed at `0x2000`, and on the second pass the branch is
taken.  The wrong-path `MOV` has been decoded on the first pass, so the
core has it at once (golden 018's warm case), and it reads `*R24` --
`0x2000` -- from memory before the branch resolves.  The core runs this
golden with PSW.V = 1 and only page 0 mapped (Pre-state), so that read
faults.  The architectural trace does not contain it: no record, no
exception, the run continues at the branch target.

The image is 12 words = 48 bytes; 12 records retire.

## How this file was derived

By hand from the printed tables, before either model ran it.  The parcels
were written from the encoding tables and then disassembled with
`asm/hobbit_asm.py --disasm` as a cross-check (it agreed; nothing was
changed).  Neither `sem/` nor `bsv/` produced or corrected any field.

## Pre-state

The fixed pre-state of `README.md` -- PC 0, SP `0x100`, MSP `0x180`,
memory zero except the image -- for the hand derivation and for
`sem/`, with PSW `0x00000200`.

The core runs it with PSW `0x00010200`: the same, plus V (bit 16,
virtual addressing, Table 1-8 p. 1-14).  Segment 0 is paged with its page
table at `0x1000` (segment entry `0x00001001`, Table 2-1 p. 2-5); page 0
maps to frame 0 (`0x00000807`, Table 2-3 p. 2-7) and every other page
is invalid (entry 0), so the image, the stack and every word this
program *executes* on are in page 0 and `0x2000` is the one address that
faults.  No retired instruction touches page 1 or above, so the
architectural trace is the same with V = 0 and V = 1 -- which is the
point: the faulting read is not architectural.  `bsv/run_golden.sh`
builds that harness for this stem (the tables of `HobbitCoreMmuTb.bsv`).
